# 하네스

> 하네스는 네 문서를 매 답마다 검토해, 무엇이 추가돼야 완성인지와 다음 단계를 알려 주는 CLI다.
> 의존성 없이 Node 20 이상에서 돈다.
> 하네스는 문서 내용을 쓰지 않는다. 읽고 세고 알려 주며, 빈 틀을 만들고 결과물을 옮기기만 한다.

---

## 1. 명령

| 명령 | 하는 일 |
|---|---|
| `node scripts/pp.mjs init <폴더> [기능 이름]` | 지금 단계에 필요한 파일 가운데 없는 것만 빈 틀로 만든다 (처음엔 `brief.md`만) |
| `node scripts/pp.mjs check <폴더> [--json]` | 지금 단계와 완성도, 추가돼야 완성인 것, 다음 할 일을 보여 준다 |
| `node scripts/pp.mjs lock <폴더>` | 2-4단계까지 잠금 말고 남은 것이 없을 때 요구사항 지문을 `lock.json`에 남긴다 |
| `node scripts/pp.mjs unlock <폴더>` | 잠금을 푼다. 요구사항을 고친 뒤 사람이 확인하면 다시 `lock`한다 |
| `node scripts/pp.mjs sheet <폴더>` | 요구사항 대조에 쓸 검토지를 JSON으로 낸다 (3장) |
| `node scripts/pp.mjs quotes <폴더>` | 개발 스펙이 인용할 수 있는 원문과 번호를 JSON으로 낸다 |
| `node scripts/pp.mjs export <폴더> [프로젝트 폴더] [--force] [--keep]` | 결과물을 `<프로젝트>/docs/product/{기능}/`에 내보낸다 (6장) |
| `node scripts/pp.mjs import <프로젝트 폴더> <폴더>` | 프로젝트의 결과물을 작업 폴더로 다시 읽어 온다 (6장) |
| `node scripts/pp.mjs discard <폴더>` | 내보내지 않고 작업 폴더를 지운다 |

종료 코드는 `0` 완료, `1` 아직 남음, `2` 입력이나 경로 오류다.

---

## 2. 폴더

작업 폴더는 대상 프로젝트의 `.product-planning/{feature}/`에 둔다. 폴더 이름이 영어 기능 이름이다.
`init`·`import`가 `.product-planning/.gitignore`(`*`)를 만들어 작업 파일이 git에 올라가지 않게 한다. 프로젝트 `.gitignore`는 건드리지 않는다.

```text
<프로젝트>/.product-planning/{feature}/
├─ brief.md    비즈니스 요구사항 (brief-guide.md)
├─ plan.md     기획 요구사항 (planning-guide.md)
├─ lock.json   사람이 잠근 요구사항 지문
├─ spec.md     기획 상세 스펙 (spec-guide.md)
├─ trace.json  모델이 쓴 요구사항 대조 (3장)
├─ dev.md      개발 스펙 (dev-guide.md)
└─ diagram.md  시퀀스 다이어그램 (diagram-guide.md)
```

`init`은 앞 문서가 다 통과해야 다음 파일 틀을 만든다. `check`·`sheet`·`quotes`는 아무 파일도 고치지 않는다.

---

## 3. 대조 파일

`sheet`가 내주는 검토지에는 완성 기준마다 번호, 문장, `fingerprint`가 있고, 트리의 모든 줄 경로가 함께 있다.
모델은 검토지를 보고 `trace.json`을 아래 모양으로 쓴다.

```json
{
  "R1-1": {
    "verdict": "met",
    "evidence": ["F1 › ? 수정 권한이 있는가 › **예** › ◆ 게시글 상태 › **게시됨** › [수정] 누름 → 수정 모달이 열린다"],
    "fingerprint": "검토지의 값을 그대로"
  },
  "R1-2": {
    "verdict": "missing",
    "missing": "저장한 뒤 댓글이 어떻게 되는지 나오는 줄이 있어야 완성이다.",
    "fingerprint": "검토지의 값을 그대로"
  }
}
```

| 하네스가 보는 것 | 걸리면 |
|---|---|
| 제외되지 않은 완성 기준마다 판단이 있는가 | `[대조 없음]` |
| `fingerprint`가 지금 기준 문장과 맞는가 | `[대조 낡음]` 기준이 바뀌었으니 다시 판단한다 |
| `met`의 근거 줄이 지금 트리에 있는가 | `[대조 낡음]` 근거 줄이 바뀌었으니 다시 판단한다 |
| `met`인데 근거 줄이 없는가 | `[근거 없음]` |
| `missing`인가 | `[요구사항]` 모델이 적은 추가돼야 할 것을 그대로 보여 준다 |

완성도는 제외되지 않은 완성 기준 가운데 낡지 않은 `met`의 비율이다.

## 4. 보고 모양

```text
단계  개발 › 5-4. 계약
완성도  R1 3/3 · 전체 100%
추가되어야 완성
1. [안 물어봄] "F1 › … › [수정] 누름 → 수정 모달이 열린다"를 인용한 계약이나 결정이 없다.
그 밖에 2건
다음  트리의 사용자 행동을 원문을 인용해 무엇을 보내고 성공·실패 때 무엇을 받는지 묻는다.
```

- 단계는 앞에서부터 처음으로 걸린 곳이며, 걸린 것은 그 단계의 것만 보여 준다.
- 뒤 단계에 남은 건수는 `그 밖에 N건`으로만 알린다.
- 기획이 다 끝나고 개발 파일이 없으면 단계는 `기획 완료`이고, 개발로 넘어갈지 묻게 한다.

---

## 5. 단계 판정 순서

앞 문서가 다 통과해야 뒤 문서를 본다. 번호는 `check --json`의 `step`이다.

| step | 단계 | 파일 | 작성법 |
|---|---|---|---|
| 1~6 | 기획 › 1-1 기능 이름 ~ 1-6 확정 | `brief.md` | [비즈니스 요구사항](brief-guide.md) 1·4장 |
| 7~11 | 기획 › 2-1 페르소나 ~ 3 PRD 확정 | `plan.md` | [기획](planning-guide.md) 1·6장 |
| 12~17 | 기획 › 4-1 상태 수립 ~ 4-6 확정 | `spec.md`, `trace.json` | [기획 상세 스펙](spec-guide.md) 1·5·6장 |
| 18~28 | 개발 › 5-1 결정 ~ 5-11 확정 | `dev.md`, `diagram.md` | [개발 스펙](dev-guide.md) 2·5장, [다이어그램](diagram-guide.md) 4장 |

- 문장 규칙(한 줄 한 문장, 개발 용어, 모호한 말, 80자)은 `brief.md`와 `plan.md`에 걸린다. `원문:` 줄은 빼고 본다.
- 잠금(10)은 요구사항 검사가 끝난 뒤에만 본다. 지문에는 BR, 범위 밖, 페르소나, 요구사항, 완성 기준이 들어간다.
- 대조(16)는 트리 검사(12~15)가 끝난 뒤에만 보인다.
- 시퀀스 검사는 22단계, 다이어그램 확정은 28단계에서 보인다.

## 6. 결과물

결과물은 대상 프로젝트 안 `docs/product/{기능}/`에 남는 기준 문서다.

| 파일 | 만드는 법 |
|---|---|
| `prd.md` | `brief.md`와 `plan.md`를 왜 지금 → 목표 → BR → 페르소나 → 요구사항 → 범위 밖 → 제약 순서로 합친다 |
| `spec.md` | `spec.md`에서 진행표를 뺀다 |
| `dev.md` | `dev.md`에서 기획에 돌려보낼 것과 정할 것을 뺀다 |
| `diagram.md` | `diagram.md` 그대로 |

- 모든 결과물에서 상태 줄과 기능 줄을 빼고, 제목 아래에 `> 기준 문서:` 줄로 네 문서를 잇는다.
- 번호 정의에는 `<a id="r1"></a>` 앵커를 달고, 다른 곳의 번호는 그 앵커로 가는 링크로 바꾼다.
- `prd.md`·`spec.md`의 번호 항목 아래에는 그 번호를 쓰는 항목을 `쓰는 곳:` 줄로 붙인다.
- `export`는 기획이 완료일 때만 된다. 개발까지 완료면 네 문서를, 개발 파일이 없으면 두 문서만 낸다.
- 개발을 쓰는 중이면(파일은 있는데 완료가 아님) 내보내지 않는다.
- 네 문서를 냈을 때만 작업 폴더를 지운다. `--keep`이면 남긴다. 하네스 파일이 아닌 것이 든 폴더는 지우지 않는다.
- 작업 폴더를 지워 `.product-planning/`에 `.gitignore`만 남으면 그것도 지운다.
- 작업 폴더가 `<프로젝트>/.product-planning/{기능}/`이면 `export`의 프로젝트 폴더는 생략한다.
- 결과 파일이 이미 있으면 `--force` 없이는 덮어쓰지 않는다. `import`로 읽어 와 고친 뒤에는 `--force`로 낸다.
- `import`는 링크와 앵커, 쓰는 곳 줄을 떼고 PRD를 `brief.md`와 `plan.md`로 나눈다. 상태는 `확정`, 요구사항은 잠근 채로, 진행표는 트리에서 다시 만든다.
- `trace.json`은 결과물에 없으므로 `import` 뒤에는 요구사항 대조를 다시 한다.
