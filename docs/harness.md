# 하네스

> 하네스는 기획과 SDD 스펙을 매 답마다 검토해, 무엇이 추가돼야 완성인지와 다음 단계를 알려 주는 CLI다.
> 의존성 없이 Node 20 이상에서 돈다.
> 하네스는 문서를 쓰지 않는다. 읽고 세고 알려 주기만 한다.

---

## 1. 명령

| 명령 | 하는 일 |
|---|---|
| `node scripts/pp.mjs init <폴더> <기능 이름>` | 없는 파일만 빈 틀로 만든다 (기획이 확정되기 전에는 `sdd.md`를 만들지 않는다) |
| `node scripts/pp.mjs check <폴더>` | 지금 단계와 완성도, 추가돼야 완성인 것, 다음 할 일을 보여 준다 |
| `node scripts/pp.mjs check <폴더> --json` | 같은 결과를 JSON으로 낸다 |
| `node scripts/pp.mjs sheet <폴더>` | 요구사항 대조에 쓸 검토지를 JSON으로 낸다 |
| `node scripts/pp.mjs export <폴더> <결과 폴더>` | 완료된 PRD·요구사항 정의서·SDD 스펙을 세 파일로 내보내고 작업 폴더를 지운다 (6장) |
| `node scripts/pp.mjs discard <폴더>` | 내보내지 않고 작업 폴더를 지운다 |

종료 코드는 `0` 완료, `1` 아직 남음, `2` 입력이나 경로 오류다.

---

## 2. 폴더

작업 폴더는 프로젝트 밖 `~/.product-planning/work/{feature}/`에 둔다.

```text
~/.product-planning/work/{feature}/
├─ plan.md     비개발자용 기획 (planning-guide.md)
├─ sdd.md      개발자용 SDD 스펙 (sdd-guide.md)
└─ trace.json  모델이 쓴 요구사항 대조 (3장)
```

세 파일 모두 사람이 읽을 수 있고, `check`·`sheet`는 아무 파일도 고치지 않는다.

---

## 3. 대조 파일

`sheet`가 내주는 검토지에는 완성 기준마다 번호, 문장, `fingerprint`가 있고, 트리의 모든 줄 경로가 함께 있다.
모델은 검토지를 보고 `trace.json`을 아래 모양으로 쓴다.

```json
{
  "R1-1": {
    "verdict": "met",
    "evidence": ["게시글 수정 › ? 수정 권한이 있는가 › **예** › ◆ 게시글 상태 › **게시됨** › [수정] 누름 → 수정 모달이 열린다"],
    "fingerprint": "검토지의 값을 그대로"
  },
  "R1-2": {
    "verdict": "missing",
    "missing": "저장한 뒤 댓글이 어떻게 되는지 나오는 줄이 있어야 완성이다.",
    "fingerprint": "검토지의 값을 그대로"
  }
}
```

| 하네스가 보는 것 | 걸리면 |
|---|---|
| 제외되지 않은 완성 기준마다 판단이 있는가 | `[대조 없음]` |
| `fingerprint`가 지금 기준 문장과 맞는가 | `[대조 낡음]` 기준이 바뀌었으니 다시 판단한다 |
| `met`의 근거 줄이 지금 트리에 있는가 | `[대조 낡음]` 근거 줄이 바뀌었으니 다시 판단한다 |
| `met`인데 근거 줄이 없는가 | `[근거 없음]` |
| `missing`인가 | `[요구사항]` 모델이 적은 추가돼야 할 것을 그대로 보여 준다 |

완성도는 제외되지 않은 완성 기준 가운데 낡지 않은 `met`의 비율이다.

## 4. 보고 모양

```text
단계  SDD 스펙 › 4. 단위별 트리
완성도  R1 1/2 · 전체 50%
추가되어야 완성
1. [빠진 상태] 게시글 수정 › ◆ 게시글 상태 아래 '삭제됨' 갈래가 없다.
2. [요구사항] R1-2 저장한 뒤 댓글이 어떻게 되는지 나오는 줄이 있어야 완성이다.
다음  위 2건을 질문으로 바꿔 사람에게 묻는다.
```

- 단계는 앞에서부터 처음으로 걸린 곳이며, 걸린 것은 그 단계의 것만 보여 준다.
- 뒤 단계에 남은 건수는 `그 밖에 N건`으로만 알린다.
- 걸린 것이 없으면 다음 단계로 무엇을 할지 한 줄로 알려 준다.

---

## 5. 단계 판정 순서

| 순서 | 단계 | 넘어가는 조건 |
|---|---|---|
| 1 | 기획 › 요약과 목표 | 한 줄 요약(1~3줄)과 배경이 있고, 목표마다 `확인:`이 있다 |
| 2 | 기획 › 페르소나 | 페르소나마다 원하는 것과 행동 패턴이 있다 |
| 3 | 기획 › 요구사항 | 요구사항마다 누구·왜·우선순위(꼭·나중에)가 있고, 모든 페르소나가 요구사항에 쓰인다 |
| 4 | 기획 › 완성 기준 | 요구사항마다 완성 기준이 있고 번호가 맞다 |
| 5 | 기획 › 범위와 확정 | 범위 밖과 선택 구역이 채워졌고(없으면 `없음`), 작성자가 있고, 정할 것이 비었고, 상태가 `확정`이다 |
| 6 | SDD › 1. 상태 수립 | 상태표에 행이 있다 |
| 7 | SDD › 2. 조건 수립 | 조건표에 행이 있다 |
| 8 | SDD › 3. 단위 나누기 | 모든 요구사항이 피쳐에 들어가고 진행표가 트리와 맞다 |
| 9 | SDD › 4. 단위별 트리 | 형식 검사가 0건이다 |
| 10 | SDD › 5. 요구사항 대조 | 모든 완성 기준이 낡지 않은 `met`이다 |
| 11 | SDD › 6. 확정 | 상태가 `확정`이다 |

문장 규칙(한 줄 한 문장, 개발 용어, 모호한 말, 80자)은 기획 전체에 걸리며 그 줄이 속한 단계에서 보인다.

---

## 6. 결과물만 남기기

작업 흔적 없이 결과물 세 파일만, 그때마다 고른 폴더에 남긴다.

| 남는 것 | 남지 않는 것 |
|---|---|
| 사람이 고른 폴더의 `{feature}-prd.md`(PRD), `{feature}-requirements.md`(요구사항 정의서), `{feature}-sdd.md`(개발자용 SDD 스펙, 맨 위에 두 기획 문서 링크) | 작업 폴더, `trace.json`, 진행표, 상태 줄, 정할 것, `없음`인 선택 구역 |

- 작업 폴더는 처음부터 프로젝트 밖에 두므로 프로젝트에는 결과물 말고 아무것도 생기지 않는다.
- `export`는 완료(`check` 종료 코드 0)일 때만 되고, 결과물을 쓴 뒤 작업 폴더를 지운다.
- 하네스 파일이 아닌 것이 든 폴더는 엉뚱한 폴더일 수 있으니 지우지 않는다.
- `{feature}`는 작업 폴더 이름이다.
- PRD와 요구사항 정의서는 `plan.md` 하나에서 만든다. 각 문서에 담는 것은 [기획 작성법](planning-guide.md) 8장에 있다.
- 세 파일 중 하나라도 이미 있으면 `--force` 없이는 덮어쓰지 않는다. `--keep`이면 작업 폴더를 남긴다.
