# 기획 파이프라인 설계서

> 작성일 2026-09-29 · v4 (플러그인 v0.8 기준)
> 코드가 아니라 **기획을 어떻게 만들고 검토하는지**에 대한 설계다. 구현 방식은 11장에서 개념 수준으로만 다룬다.
> 특정 회사·제품·도구에 종속되지 않는다. 도구 이름은 예시로만 쓰며, 설계는 도구 유형(문서 도구, 디자인 도구, 화이트보드 도구, 이슈 트래커)을 기준으로 한다.

---

## 0. 한 장 요약

| 항목 | 내용 |
|---|---|
| 만드는 것 | 제품·도메인과 무관한 개인 플러그인. 어떤 입력으로 시작해도 **같은 구조, 같은 품질의 기획서**(PRD·시나리오·플로우차트·기능명세서)를 만든다 |
| 핵심 아이디어 | 기획서를 **요소와 관계로 이루어진 모델**로 다룬다. 좋은 기획인지는 "필요한 관계가 빠짐없이 이어졌는가"로 판정한다 |
| 일관성 보장 | 모델은 판단만 하고, 문서·그림·출력은 정해진 규칙으로 렌더링한다 |
| 생산성 | 사람은 사실을 한 번만 적는다. 화면·플로우차트·엣지 케이스·완료 조건 초안은 파생된다 |
| 입구 3개 | 새로 만들기 / 기존 자료 보완하기 / 기존 기획서 변경하기. 셋 다 같은 검토 관문과 같은 출력을 거친다 |
| 출력 | 사람이 읽는 **HTML 네 파일**(PRD·시나리오·플로우차트·기능명세서)과 AI·출력 어댑터가 읽는 **`model.json`**(8.5절). 사람용은 개발에 필요한 것만, 데이터는 전부 담는다. 디자인·화이트보드·문서·이슈 도구로는 `model.json`을 입력으로 9장 **출력 대상 가이드**대로 옮긴다 |
| 범위 밖 | 비주얼 디자인, 코드 생성, 제품 방향 결정 (사람의 몫) |

## 1. 원칙

1. **한 사실은 한 곳에만 적는다.** 같은 내용을 표·그림·본문에 반복해서 쓰지 않는다. 한 번 적고 나머지는 파생한다.
2. **품질은 관계로 판정한다.** "좋아 보인다"가 아니라 "요구사항마다 완료 조건이 있는가"처럼 셀 수 있는 규칙으로 판정한다.
3. **모든 문장에는 출처가 있다.** 출처가 없으면 `가정`으로 표시한다. 가정은 숨기지 않고 센다.
4. **모델은 판단만 한다.** 수집, 초안 작성, 충돌 해석, 휴리스틱 판단은 모델이 하고, 형식·그림·출력은 규칙이 만든다.
5. **판단에도 근거를 요구한다.** 모델이 휴리스틱 위반을 지적하면 어느 요소(ID)에서 무엇이 빠졌는지를 함께 적어야 한다.
6. **방향은 사람이 정한다.** 제품 방향, 우선순위, 충돌했을 때의 선택은 사람이 결정하고 결정 기록에 남긴다.
7. **본체는 도메인을 모른다.** 도메인 용어·역할·권한 모델·화면 폭·원천 위치는 프로젝트 프로필에 둔다.
8. **사람에게는 이름을, 도구에게는 ID를 준다.** 문서·그림·디자인 파일에는 한글 이름만 보인다. ID는 요소끼리 연결하고 대상 도구와 매핑할 때만 쓴다 (3.1절).

## 2. 전체 구조

```
                ┌─ 새로 만들기 ─────────────┐
입구 ───────────┼─ 보완하기 (기존 자료) ────┼──▶  기획 모델  ──▶  검토 관문  ──▶  렌더  ──▶  출력 어댑터
                └─ 변경하기 (기존 기획서) ──┘    (요소+관계)     (5장 기준)   (HTML 4 + model.json) (9장 가이드)
                                                     ▲
                                              기반 (10장): 제품 기준서 · 컨텍스트 사전 · 결정 기록
```

- 기획 모델은 하나뿐이다. 입구는 모델을 채우는 방법만 다르다.
- 검토 관문을 통과하지 못하면 렌더는 되지만 문서 맨 위에 "착수 불가"와 사유가 표시된다.
- 출력은 항상 같은 모델에서 나온다. 대상이 바뀌어도 내용은 같다.
- 모든 출력 어댑터와 AI의 입력은 `model.json`(첫 HTML 안에도 같은 데이터)이다. 어떤 대상으로 옮길지는 빌드한 뒤에 정한다.

## 3. 기획 모델: 요소와 관계

### 3.1 요소

| 요소 | 뜻 | 내부 ID 접두어 | 예 (범용) |
|---|---|---|---|
| 서비스·시스템 | 기획이 걸치는 서비스, API 서버, 외부 시스템. 서비스마다 앱이 속한다 | `SYS` | 코치 서비스, 선수 서비스, 핵심 API |
| 사용자 유형 | 목표와 불편함이 다른 사용자 집단. 사람이 아닌 자동 처리 주체도 포함한다 | `U` | 관리자, 일반 사용자, 시스템 |
| 앱 | 사용자가 만나는 표면과 플랫폼 | `A` | 관리자 웹(웹), 사용자 앱(iOS·Android) |
| 요구사항 | 누가 무엇을 왜 하려는가 | `R` | "관리자는 항목을 배정하려고 대상을 고른다" |
| 시나리오 | 요구사항을 이루는 단계의 순서 (기본·대안·예외) | `S` | 항목 배정 · 기본 흐름 |
| 개체 | 다루는 대상 | `E` | 항목, 댓글 |
| 상태 | 개체가 가질 수 있는 값 | `ST` | 예정, 진행 중, 완료 |
| 동작 | 사용자가 개체에 하는 일. 입력(검증 형식), 부르는 API, 다른 앱 영향을 가진다 | `AC` | 만들기, 수정, 마감 |
| 화면 | 동작이 일어나는 곳 | `SC` | 항목 목록 |
| 화면 요소 | 화면 안의 영역·버튼·입력 | `SC-01.e3` | 항목 목록 › 새 항목 버튼 |
| 규칙 | 계산·판정·검증 규칙 (입력 → 결과) | `RU` | 진행률 계산 |
| 완료 조건 | 상황 → 행동 → 결과 | `C` | 항목 배정 3 · 권한 없는 사용자가 들어올 때 |
| 문구 | 사용자에게 보이는 안내. 공통 9종과 기능별(성공·실패·확인 창·알림) | — | 입력 내용을 확인해 주세요 |
| 이벤트 | 측정을 위해 기록하는 사건 | `EV` | 항목 생성 완료 |
| 지표 | 성공을 판정하는 수치 | `M` | 주간 배정 완료율 |
| 정할 것 / 결정 | 미결 질문과 그 결론 | `Q` / `D` | 완료된 항목을 수정할 수 있는가? |
| 출처 | 사실의 근거 | — | 코드, 스키마, 문서, 데이터, 레퍼런스, 결정, 가정 |

**이름과 ID**

모든 요소는 한글 이름과 내부 ID를 함께 가진다.

- **이름**은 사람이 읽고 부르는 표기다. 문서 본문, 그림, 디자인 파일, 티켓 제목에는 이름만 나온다.
- **ID**는 바뀌지 않는 연결 키다. 이름을 바꿔도 ID는 그대로라서, 한 곳에서 이름을 바꾸면 모든 출력에 자동으로 반영된다.
- ID는 사람용 문서에 보이지 않는다. `model.json`, HTML 속성, 외부 도구의 메타데이터에만 남는다.

| 요소 | 이름 짓는 법 | 예 |
|---|---|---|
| 사용자 유형 | 역할 명사 | 배정 관리자 |
| 요구사항 | "누가 무엇을 한다" 한 문장 | 관리자가 항목을 배정한다 |
| 시나리오 | 요구사항 + 흐름 종류 | 항목 배정 · 기본 흐름 |
| 개체 · 상태 | 명사 | 항목 · 진행 중 |
| 동작 | 동사형 | 항목 마감하기 |
| 화면 | 명사구 | 항목 목록 |
| 화면 상태 | 화면 · 상태 | 항목 목록 · 빈 화면 |
| 화면 요소 | 화면 › 요소 | 항목 목록 › 새 항목 버튼 |
| 완료 조건 | 요구사항 아래 순번 + 상황 요약 | 항목 배정 3 · 권한 없는 사용자가 들어올 때 |
| 정할 것 | 질문 문장 그대로 | 완료된 항목을 수정할 수 있는가? |
| 결정 | 결정 내용 한 문장 | 완료된 항목은 수정할 수 없다 |

같은 종류의 요소끼리 이름이 겹치면 안 된다 (3.2절 마지막 줄). 이름에 쓰는 도메인 단어는 용어 사전을 따른다.

### 3.2 관계

관계는 방향과 개수 조건을 가진다. 개수 조건이 곧 검토 규칙이 된다 (5.1절).

| 관계 | 조건 |
|---|---|
| 요구사항 → 사용자 유형 | 정확히 1 |
| 요구사항 → 우선순위 | 정확히 1 (필수·권장·선택) |
| 요구사항 → 시나리오 | 1 이상 |
| 요구사항 → 완료 조건 | 1 이상 |
| 시나리오 단계 → 화면 | 단계마다 1 (어디서 하는지, 4.1절 자동 도출) |
| 동작 → 개체 | 정확히 1 |
| 동작 → 시나리오 단계 | 1 이상 (요청한 시나리오에 쓰이지 않는 동작은 요청 밖이다) |
| 개체 → 동작 | 1 이상 |
| 동작 → 상태 변화 | 상태를 바꾸는 동작이면 "어떤 상태에서 어떤 상태로"가 1 이상 |
| 동작 × 사용자 유형 × 개체 상태 → 가능 여부 | **모든 칸이 채워짐** (허용·숨김·비활성·불가 중 하나) |
| 상태 → 들어오는 전이 | 1 이상 (시작 상태는 예외) |
| 상태 → 나가는 전이 | 1 이상 (끝 상태는 예외) |
| 상태 → 화면 표시 | 1 이상 (사용자에게 어떻게 보이는가) |
| 화면 → 들어오는 이동 | 1 이상 (진입점은 예외) |
| 화면 → 나가는 길 | 1 이상 |
| 화면 → 화면 상태 | 프로필의 화면 상태 전부 (기본 5종) |
| 동작 (다른 앱에 영향) → 받는 쪽 화면이나 알림 | 1 이상 |
| 입력 요소 → 검증 형식 | 정확히 1 (형식과 범위. 추가 조건은 글) |
| 되돌릴 수 없는 동작 → 확인 창 문구 | 정확히 1 |
| 다른 앱에 영향 → 알림 문구 | 정확히 1 |
| 기획서 → 공통 문구 (입력 오류·권한 없음·빈 화면·불러오기 오류·통신 실패·알 수 없는 오류·로그인 만료·확인·취소) | 각각 1 |
| 서버를 거치는 동작 → 실패 처리 | 실패 유형마다 1 |
| 지표 → 이벤트 | 1 이상 |
| 정할 것 → 담당자, 막는 대상 | 각각 1 |
| 모든 사실 → 출처 | 정확히 1 |
| 모든 요소 → 한글 이름 | 정확히 1. 같은 종류 안에서 중복 없음 |

### 3.3 관계도 (모두 모델에서 자동으로 그린다)

| 관계도 | 보여 주는 것 | 누가 주로 보나 |
|---|---|---|
| **개체 관계도** | 개체끼리의 포함·참조 관계. 예: 목표 1 — N 항목 | 개발, 기획 |
| **상태 전이도** | 개체별 상태와 전이. 전이마다 "누가, 어떤 동작으로" | 기획, 개발, QA |
| **동작 가능표** | 사용자 유형 × 동작 × 개체 상태의 가능 여부 | 전원. 권한과 상태의 연결고리가 한 표에 모인다 |
| **전체 흐름** | 서비스 틀 안의 앱별 요구사항, 먼저 해야 할 수 있는 순서, 다른 서비스 영향, API 호출 | 전원 |
| **플로우차트** | 시나리오(순서) · 기능(판단 갈래) · 페이지(화면 상태) (4.2절) | 기획, 개발, 디자이너 |

추적표(요구사항 → 시나리오 → 화면 → 완료 조건)와 화면 목록은 `model.json`에만 둔다. 사람용 문서에는 보이지 않는다.

**동작 가능표**가 이 설계의 중심이다. 권한과 상태가 따로 정의되면 "완료된 항목은 누가 수정할 수 있나" 같은 질문이 개발 도중에 나온다. 둘을 한 표에서 칸으로 강제하면 빈칸이 곧 정할 것이 된다.

```
동작 가능표 예 (개체: 항목)
                   │ 예정   │ 진행 중 │ 완료   │ 조기 마감
───────────────────┼───────┼────────┼───────┼─────────
관리자(배정한 본인) │ 수정 ✓ │ 수정 ✓  │ 수정 ✗ │ 수정 ✗
관리자(다른 사람)   │ 숨김   │ 숨김    │ 숨김   │ 숨김
보기 전용 사용자    │ 숨김   │ 숨김    │ 숨김   │ 숨김
```

## 4. 단계

단계마다 앞 단계의 요소를 참조하므로, 앞 단계의 관문을 통과해야 다음 단계의 검사가 의미를 가진다. 되돌아가는 것은 언제든 가능하다.

| 단계 | 질문 | 사람이 적는 것 | 자동으로 생기는 것 | 통과 기준 (객관) |
|---|---|---|---|---|
| **0. 기반** (프로젝트당 1회) | 우리는 무엇을 위해 판단하나 | 제품 기준서 (10.1절) | 컨텍스트 사전: 권한·상태·API·컴포넌트·이벤트·용어 | 기준서 필수 항목 모두 채움. 사전 추출 성공 |
| **1. 정의** | 무엇을, 왜, 누구를 위해, 무엇이면 성공인가 | 구성(새 서비스·기능 추가·프로젝트, 서비스·앱·플랫폼·API), 문제, 근거, 대상 사용자 유형, 목표 지표 | 기준서 원칙과의 충돌 경고, 지표에 연결할 기존 이벤트 후보 | 구성이 채워짐. 문제 문장에 `가정`이 아닌 출처 1개 이상. 지표가 측정 가능 (기존 이벤트 또는 신규 이벤트 정의) |
| **2. 시나리오** | 사용자는 무엇을 하나 | 요구사항 한 줄과 우선순위, 시나리오 단계 | 시나리오 플로우차트, 전체 흐름 | 모든 요구사항에 사용자 유형·우선순위·시나리오 |
| **3. 모델링** | 무엇이 어떻게 바뀌나 | 개체와 상태·전이, 동작(입력 검증 형식, 부르는 API, 다른 앱 영향), 동작 가능표의 칸, 규칙 | 상태 다이어그램, 동작 가능표 빈칸, 기능 플로우차트, 엣지 케이스 (4.3절) | 동작 가능표에 빈칸 0. 도달할 수 없는 상태 0. 빠져나갈 수 없는 상태 0 (끝 상태 제외). 다른 앱에 영향이 있는 동작마다 받는 쪽이 있음 |
| **4. 흐름과 문구** | 어디서 어떻게 하고 무엇을 보여 주나 | 자동 흐름에서 바꿀 곳, 문구(공통 9종, 확인 창, 다른 앱 알림, 성공·실패) | **화면·이동 (4.1절)**, 페이지 플로우차트, 화면 상태 기본값, 엣지 케이스 기대 결과 | 고아 화면 0. 모든 시나리오 단계가 화면에 연결됨. 문구 경고 0. 엣지 케이스가 모두 플로우차트에 있음 (`flow-coverage`). 그림 겹침 0 |
| **5. 완료 조건** | 무엇이면 끝났나 | 초안 검토와 수정 | 초안 자동 생성: 동작 가능표 칸마다, 상태 전이마다, 다루는 예외마다 | 모든 요구사항·전이에 완료 조건 1개 이상. 동작 가능표의 "숨김·비활성·불가" 칸마다 1개 이상 |
| **6. 검토** | 좋은가 | 이슈 수용·기각 결정 | 관계 규칙 결과, 휴리스틱·워크스루 이슈, 정량 지표, 품질 점수 (5장) | 심각도 3~4 이슈 0 (또는 결정 기록으로 수용). 착수를 막는 정할 것 0 |
| **7. 빌드·게시** | 누가 어디서 읽나 | 게시 대상 선택 | 사람용 HTML 네 파일, `model.json`, 프롬프트, 어댑터 출력, 파생 산출물 (6.2절) | 게시 후 다시 읽어 요소 수 대조 (9.3절) |
| **8. 시안 대조** (디자이너 시안 후) | 시안이 기획을 다 담았나 | 차이 수용 여부 | 화면 × 상태 누락, 문구 차이, 끊긴 이동 목록 | 누락 0 또는 결정 기록 |

단계를 이렇게 나눈 이유는 다음과 같다.
- 흔한 PRD는 정의(1)와 화면 설계(4)만 있고 **모델링(3)이 없다.**
- 그래서 권한·상태·예외가 개발 도중에 정의된다 (예: "완료된 항목을 수정할 수 있는가"가 착수 후 티켓에서 정해짐).
- 모델링을 화면 설계보다 앞에 두면 화면은 "모델을 보여 주는 곳"이 되고, 빈칸이 화면을 그리기 전에 드러난다.

### 4.1 화면 흐름 자동 도출

사람은 흐름을 그리지 않는다. 파이프라인이 시나리오와 모델에서 화면과 이동을 만들고, 판단마다 적용한 규칙을 남긴다. 모델의 추측이 아니라 정해진 규칙이므로 같은 입력이면 항상 같은 흐름이 나온다.

**입력**: 시나리오 단계 (누가, 어느 앱에서, 어떤 동작), 동작 (종류, 입력 항목, 되돌릴 수 있는지, 다른 앱 영향), 동작 가능표, 프로필 값 (모달 기준 입력 수)

**판단 규칙**

| # | 상황 | 판단 |
|---|---|---|
| F1 | 여러 개를 보는 동작 | '{개체} 목록' 화면 |
| F2 | 하나를 보는 동작 | '{개체} 상세' 화면 |
| F3 | 만들기·수정이고 입력 항목이 모달 기준 이하 (기본 3개) | 지금 화면 위에 뜨는 모달 |
| F4 | 만들기·수정이고 입력 항목이 모달 기준 초과 | '{개체} 만들기' · '{개체} 수정' 화면 |
| F5 | 입력이 없는 동작 | 지금 화면의 버튼. 이동하지 않는다 |
| F6 | 되돌릴 수 없는 동작 | 동작 앞에 확인 창을 끼워 넣는다 |
| F7 | 만들기를 마침 | 상세 화면이 있으면 상세로, 없으면 목록으로 간다 |
| F8 | 수정·모달·확인 창을 마침 | 연 화면으로 돌아간다 |
| F9 | 다른 앱에 영향을 주는 동작 | 받는 앱에 '알림' 진입점을 두고 받는 쪽 화면으로 잇는다 |
| F10 | 시나리오 단계의 순서 | 앞 단계의 화면에서 다음 단계의 화면으로 이동을 만든다 |
| F11 | 권한 없음·오류·빈 데이터 | 흐름의 새 화면이 아니라 해당 화면의 상태로 둔다 |
| F12 | 자동 처리 주체(`automatic` 사용자 유형)의 단계 — 기한 도래·기간 종료처럼 규칙으로 저절로 일어나는 일 | 새 화면·이동을 만들지 않고 결과가 보이는 그 개체의 상세 화면(없으면 목록 화면)에 연결한다. 단계의 앱에 있는 화면을 먼저 쓴다. 보이는 화면이 없으면 정할 것으로 올린다 |

### 4.2 플로우차트 자동 도출

플로우차트는 세 종류이고 같은 사실을 두 번 그리지 않는다. 판단은 사람이 그리지 않고 모델에서 나온다.

| 종류 | 한 장의 단위 | 보이는 것 | 보이지 않는 것 |
|---|---|---|---|
| 전체 흐름 | 기획서 하나 | 서비스마다 큰 틀, 그 안에 앱 틀과 요구사항. 먼저 만들어야 쓸 수 있는 순서(한 요구사항이 만든 개체를 다른 요구사항이 씀, 검은 선), 다른 서비스로 가는 영향(파란 선), API 서버 호출(보라 점선). 선은 틀 위 통로를 지난다 | 화면 단위 이동 (페이지 플로우차트에 있다), 판단 (기능 플로우차트에 있다) |
| 시나리오 | 시나리오 하나 | 시작(누가·어느 앱) → 기능 순서 → 그때 바뀌는 상태 → 끝 | 판단 (기능 플로우차트에 있다) |
| 기능 | 사람이 하는 동작 하나 | 시작 → FC1~FC4 판단과 갈래 → 성공 안내 → 상태 변화 → 다른 앱 알림 → 끝 | 문구 원문·권한 값 (기능명세서에 있다) |
| 페이지 | 화면 하나 (모달·확인 창·알림 제외) | 권한이 있나 → 불러오는 중 → 불러왔나(아니오면 다시 시도) → 데이터가 있나(목록·상세) → 화면 표시와 거기서 할 수 있는 것 → 끝 | 화면 안 배치 (디자인의 몫) |

| 규칙 | 판단이 생기는 조건 | 아니오 갈래 |
|---|---|---|
| FC0 권한 | 동작 가능표에서 이 기능을 전혀 할 수 없는 사용자가 있는 동작 | 끝: 권한 없음 안내 |
| FC1 상태 조건 | 할 수 있는 사람도 못 하는 상태가 있는 동작 | 끝: 할 수 없음 |
| FC2 입력 규칙 | 형식이나 추가 조건이 있는 입력 | 안내: 입력 오류 → 다시 입력 (처리로 되돌아감) |
| FC3 확인 창 | 되돌릴 수 없는 동작 | 끝: 취소 |
| FC4 서버 결과 | 서버 동작 | 기능 고유 실패와 공통 오류(통신 실패·알 수 없는 오류·로그인 만료)마다 안내 → 끝 |

**하네스 루프**: 그린 그림은 겹침을 검사해 간격을 넓혀 다시 그리고, 엣지 케이스가 플로우차트에 빠지면 `flow-coverage`로 알린다. 그림과 엣지 케이스가 서로를 검증한다.

자동 처리 단계(`automatic` 사용자 유형)는 기능 플로우차트를 만들지 않고, 시나리오 플로우차트에 처리와 상태 변화로만 나온다.

### 4.3 엣지 케이스 자동 도출과 문구

개발자·QA가 확인할 경우는 사람이 적지 않는다. 모델에서 기능마다 전부 뽑고(산출물 명세 3.3절 `edgeCases`), 사람 문서에는 묶어서 보인다.

| 분류 | 어디서 나오나 | 기대 결과에 쓰는 문구 |
|---|---|---|
| 입력 | 입력 형식의 경계값 (비움·공백·최소-1·최소·최대·최대+1·목록 밖·형식 밖·용량·개수·추가 조건) | 입력의 `error`, 없으면 공통 `inputError` |
| 권한 | 동작 가능표에서 가능이 아닌 칸 | 숨김·비활성은 보이는 방식, 불가는 동작의 `denied`, 없으면 공통 `denied` |
| 상태 | 상태 전이 | 도착 상태 |
| 확인 창 | 되돌릴 수 없는 동작의 취소 | 아무것도 바뀌지 않음 |
| 서버 | 실패 안내마다, 공통 `network`·`unknown`·`sessionExpired`, 처리 중 다시 누름 | 실패의 `message`, 공통 문구 |
| 화면 | 목록·상세의 프로필 화면 상태 | 빈 화면은 동작의 `empty` 또는 공통 `empty`, 오류는 공통 `loadError`, 권한 없음은 `denied` |
| 다른 앱 | 다른 앱 영향 | 알림 `message` |
| 자동 | 규칙으로 일어나는 전이의 조건 직전·순간 | 유지 / 도착 상태 |

문서에서 묶는 규칙: 모든 기능에 같은 것(권한 값의 뜻, 입력 오류 처리, 중복 요청, 화면 상태, 공통 문구)은 기능명세서 맨 위에 한 번. 기능마다는 서로 다른 원인만 "막는 경우" 한 줄. 경계값 하나하나는 데이터에만.

문구는 인터뷰에서 받는다. 공통 문구 9종은 한 번, 확인 창 문구와 다른 앱 알림 문구는 기능마다. 빠지면 경고가 나고 100%가 되지 않는다.

## 5. 검토 기준

검토는 다섯 겹으로 한다. 위로 갈수록 기계가 판정하고, 아래로 갈수록 모델이 판단하되 근거를 남긴다.

### 5.1 관계 규칙 (기계 판정)

3.2절의 개수 조건을 그대로 검사한다. 결과는 통과/실패와 위반한 요소의 이름 목록이다. 사람의 해석이 끼지 않는다.

### 5.2 예외 상황 표준 목록 (기계 판정: 다뤘는가)

모든 화면과 동작에 대해 아래 항목을 "다룸" 또는 "해당 없음: 사유"로 표시해야 한다. 내용이 적절한지는 5.3과 5.4에서 본다.

| 분류 | 항목 |
|---|---|
| 데이터 양 | 0건 · 1건 · 최대치 · 최대치 초과 · 매우 긴 문자열 |
| 참조 | 참조 대상이 삭제됨 · 참조 대상의 소속이 바뀜 |
| 권한 | 권한 없음 · 사용 중에 권한 회수 · 보기 전용 |
| 시간 | 시작일·종료일 당일 · 과거 날짜 · 미래 날짜 · 마감 이후 · 시간대 차이 |
| 동시성 | 다른 사용자가 같은 대상을 동시에 수정·삭제 |
| 네트워크 | 실패 · 느림 · 같은 요청 중복 제출 |
| 흐름 | 중간 이탈 · 뒤로 가기 · 새로고침 · 링크로 직접 진입 |
| 교차 앱 | 받는 쪽 앱이 구버전 · 알림 꺼짐 · 받는 쪽이 아직 보지 않음 |
| 입력 | 필수값 누락 · 형식 오류 · 허용하지 않는 파일 형식·크기 |

프로필에서 도메인 항목을 추가할 수 있다. 본체 목록은 줄일 수 없다.

### 5.3 휴리스틱 평가 (Nielsen 10을 확인 질문으로 바꿈)

휴리스틱을 "읽고 느끼는 원칙"이 아니라 **모델 요소에 대한 질문**으로 바꿨다. 판정 방식이 "기계"인 항목은 관계 규칙처럼 자동으로 판정된다.

| # | 휴리스틱 | 확인 질문 | 판정 |
|---|---|---|---|
| 1 | 시스템 상태를 알린다 | 서버를 거치는 모든 동작에 진행 중 표시, 성공 결과, 실패 결과가 있는가. 목록에 개수나 범위가 보이는가 | 기계 |
| 2 | 사용자의 말을 쓴다 | 화면 문구가 용어 사전과 일치하는가. 금지어가 없는가. 앱마다 같은 개념을 같은 말로 부르는가 | 기계 + 모델 |
| 3 | 사용자가 통제한다 | 되돌릴 수 없는 동작에 확인이나 되돌리기가 있는가. 모든 화면에 나가는 길이 있는가. 편집 중 이탈 처리가 있는가 | 기계 |
| 4 | 일관되게 한다 | 같은 종류의 동작이 같은 UX 기본값을 쓰는가. 기본값과 다르면 사유가 있는가 | 기계 |
| 5 | 오류를 예방한다 | 모든 입력에 검증 규칙이 있는가. 제약을 입력 단계에서 막는가 (선택지 제한·비활성), 제출한 뒤에 거절하는가 | 기계 (규칙 유무) + 모델 (막는 시점) |
| 6 | 기억하지 않게 한다 | 앞 단계에서 고른 값을 다시 입력하게 하지 않는가. 선택지를 목록으로 보여 주는가 | 모델, 근거로 요소 ID |
| 7 | 효율적으로 한다 | 핵심 시나리오의 단계 수가 기준 이하인가 (5.5절). 여러 대상에 같은 동작을 할 때 일괄 처리가 있는가 | 정량 |
| 8 | 필요한 것만 보여 준다 | 화면마다 주요 동작이 1개인가. 시나리오와 무관한 요소가 있는가 | 기계 (주요 동작 수) + 모델 |
| 9 | 오류에서 회복하게 한다 | 모든 실패 유형에 원인과 다음 행동을 알리는 문구, 그리고 복구 경로가 있는가 | 기계 |
| 10 | 도움을 준다 | 처음 사용할 때의 빈 화면에 시작 방법이 있는가. 계산 규칙이 화면에서 설명되는가 | 기계 + 모델 |

**구현**: 모델 판단 항목(2·5·6·8·10)은 파이프라인이 검토지로 만든다 (`spec.mjs review`). 항목마다 판단에 필요한 사실을 함께 주고, 판단은 근거 요소 ID가 있어야 받아들인다. 판단은 독립된 두 번(둘째는 별도 에이전트)을 비교해 일치율 80% 미만이면 어긋난 항목을 다시 본다 (일관성 하네스).

### 5.4 인지적 워크스루 (모델 판단, 근거 필수)

모든 기본 시나리오의 **모든 단계**에 대해 네 질문을 묻는다. 답에는 근거가 되는 화면 요소를 적어야 하고 (내부적으로 ID로 연결된다), 답할 수 없으면 이슈가 된다.

1. 사용자가 이 단계에서 무엇을 하려 할지 알까? (목표가 화면에 드러나는가)
2. 필요한 요소가 보일까? (해당 요소가 이 화면 상태에서 표시되는가)
3. 그 요소가 원하는 결과를 낼 거라고 연결 지을까? (문구·위치가 결과를 예고하는가)
4. 누른 뒤 제대로 진행됐다고 알까? (결과 피드백이 있는가)

사용자 유형마다 따로 수행한다. 같은 화면이라도 권한이 다르면 보이는 요소가 다르기 때문이다.

### 5.5 정량 지표 (시나리오별)

| 지표 | 계산 |
|---|---|
| 화면 전환 수 | 시나리오 시작부터 끝까지 이동한 화면 수 |
| 입력 수 | 사용자가 직접 입력하거나 고르는 횟수 |
| 결정 지점 수 | 사용자가 선택지를 판단해야 하는 지점 |
| 대기 지점 수 | 서버 응답이나 다른 사용자를 기다리는 지점 |

기준값은 제품 기준서의 원칙이나 현재 방식(as-is), 레퍼런스 평균에서 가져온다. 기준값이 없으면 수치만 기록하고 비교는 하지 않는다.

### 5.6 심각도 기준

| 심각도 | 기준 |
|---|---|
| 4 | 과업을 끝낼 수 없다. 또는 데이터가 사라진다 |
| 3 | 과업은 끝나지만 잘못된 결과나 오류를 부른다. 우회가 필요하다 |
| 2 | 지연이나 혼란이 생긴다. 추가 단계가 필요하다 |
| 1 | 표현만의 문제다 |
| 0 | 문제가 아니다 (기각) |

심각도 3~4가 남아 있으면 착수 불가다. 예외적으로 수용하려면 결정 기록에 사유를 남긴다.

### 5.7 문서 품질 점수

`report.json`과 `model.json`에 같은 형식으로 남는다. 사람용 문서에는 착수를 막는 것만 보인다. 새로 만든 문서든 보완한 문서든 같은 기준으로 잰다.

| 항목 | 계산 |
|---|---|
| 관계 규칙 통과율 | 통과한 규칙 / 전체 규칙 |
| 예외 상황 처리율 | "다룸"·"해당 없음" 표시 / 전체 칸 |
| 가정 비율 | `가정` 문장 / 전체 사실 문장 |
| 출처 충돌 | 서로 다른 출처가 다르게 말하는 곳의 수 |
| 막는 정할 것 | 착수를 막는 미결 수 |
| 심각도 3~4 이슈 | 수 |

**착수 가능**은 차단 이슈 0, 막는 정할 것 0일 때다. 모델 판단의 심각도 3~4가 결정 없이 남으면 차단 이슈다 (`review-severity`). `/yw-product-spec`은 여기에 통과율 100%(경고 0, 판단 누락·근거 누락·일치율 미달 포함)까지 채운 뒤 멈춘다.

## 7. 입구별 흐름

### 7.1 새로 만들기

4장의 0 → 8을 차례로 진행한다. 각 단계에서 모델이 짧게 인터뷰하고, 사람은 답하거나 초안을 고친다.

### 7.2 보완하기 (이미 조사했거나 만든 것을 채우기)

| 순서 | 할 일 | 결과 |
|---|---|---|
| 1. 수집 | PRD, 디자인 파일 메모, 티켓, 기존 문서, 코드·스키마를 연결된 도구로 모은다 | 원문 목록 (출처 포함) |
| 2. 분해 | 원문을 사실 한 문장씩 쪼개고 요소로 분류한다 | 요소 후보 + 출처 |
| 3. 대조 | 같은 요소를 다르게 말하는 출처를 찾는다. 기존 흐름 자료 (디자인 파일의 화살표 등)가 있으면 4.1절로 도출한 흐름과도 대조한다 | 충돌 목록 → 정할 것 |
| 4. 채우기 | 요소를 모델에 넣는다. 확신이 없으면 `가정` | 부분 모델 |
| 5. 공백 찾기 | 관계 규칙을 돌려 빈 관계를 찾는다 | 공백 목록 → 단계별로 정리 |
| 6. 이어가기 | 공백이 가장 앞선 단계부터 4장 흐름으로 합류한다 | 새로 만들기와 같은 관문 |

보완 모드의 첫 산출물은 **보완 보고서**다. 단계별로 채워진 비율, 충돌, 공백, 가정을 보여 준다. 원문을 고치지 않고 모델만 만든다.

### 7.3 변경하기 (이미 통과한 기획서를 바꾸기)

1. 변경 요청을 요소 단위로 적는다 (예: "완료 상태에서도 수정 허용").
2. 관계도를 따라 영향받는 요소를 찾는다 (동작 가능표 칸 → 완료 조건 → 화면 상태 → 시안 프레임 → 티켓).
3. 영향받는 요소만 다시 검토한다.
4. 이전 버전과의 차이를 "무엇이 바뀌었고 무엇을 다시 봐야 하나"로 보고한다.

### 7.4 같은 품질이 나오는 이유

- 입구는 모델을 채우는 방법만 다르고, 관문(5장)과 렌더(8장)는 하나다.
- 품질 점수(5.7절)가 같은 식으로 계산되므로 문서끼리 비교할 수 있다.
- 모델 판단(5.3절 일부, 5.4절)은 근거 ID를 요구해서 누가 돌려도 검증할 수 있다. 같은 입력을 두 번 돌려 이슈 목록이 크게 다르면 판단 지침을 고칠 대상으로 본다.

## 8. 문서 설계 (사람용 HTML과 AI용 데이터)

### 8.1 읽는 순서

사람이 읽는 문서는 네 부분뿐이다. 이것만 보고 개발할 수 있어야 하고, 같은 사실을 두 곳에 쓰지 않는다.

1. **PRD**: 해결할 문제(출처), 대상 사용자와 목표, 목표 지표(측정 이벤트), 요구사항(우선순위·누가)
2. **시나리오**: 요구사항마다 시나리오 한 줄과 확정된 완료 조건. 단계는 플로우차트에만 있다
3. **플로우차트**: 시나리오·기능·페이지마다 한 장, 한 도화지 (4.2절)
4. **기능명세서**: 공통 규칙과 공통 문구 한 번 → 개체마다 상태 다이어그램 → 기능마다 누가 · 넣는 것 · 결과 · 막는 경우

착수를 막는 것이 남아 있으면 맨 위에 알린다. 품질 점수·검사 세부·화면 목록·완료 조건 초안·추적표·결정 기록은 문서에 없고 `model.json`에만 있다 (산출물 명세 3.2절).

### 8.2 역할별로 보는 곳

| 역할 | 보는 곳 |
|---|---|
| 기획·리더 | PRD → 시나리오의 완료 조건 → 맨 위 "착수 전에 정할 것" |
| 디자이너 | 플로우차트(페이지) → 기능명세서의 문구와 화면 상태. 화면 안 배치는 디자이너가 그린다 |
| 개발 | 기능명세서(누가·넣는 것·결과·막는 경우) → 플로우차트(기능) → `model.json`의 `edgeCases` |
| QA | `model.json`의 `edgeCases` 전체 → 시나리오의 완료 조건 |

### 8.3 문장 규칙 (기계 검사)

- 한 문장에는 사실 하나만 쓴다.
- 요소는 이름으로 부른다. 본문에 내부 ID를 쓰지 않는다. 이름은 누르면 해당 요소로 이동하는 링크가 된다.
- 문장 길이 상한을 둔다 (프로필 값, 기본 80자).
- 모호한 말을 금지한다: "적절히", "필요 시", "가능하면", "~될 수 있음", "등". 목록은 끝이 닫힌 목록으로 쓴다.
- 수치에는 단위를 붙인다.
- 용어 사전에 없는 도메인 용어는 경고한다.

### 8.4 한글 용어

| 원래 용어 | 문서 표기 |
|---|---|
| Given / When / Then | 상황 / 행동 / 결과 ("이런 상황에서 → 이렇게 하면 → 이렇게 된다") |
| Acceptance Criteria | 완료 조건 |
| Persona | 사용자 유형 |
| User Story | 요구사항 |
| Edge case | 엣지 케이스 (문서에는 '막는 경우'로 묶어 보인다) |
| User flow | 플로우차트 (시나리오·기능·페이지) |
| Empty / Loading / Error / No permission / Read-only | 빈 화면 / 불러오는 중 / 오류 / 권한 없음 / 보기 전용 |
| KPI / Guardrail | 목표 지표 / 지켜야 할 지표 |
| Out of scope | 이번에 하지 않는 것 (데이터에만) |
| Open question / Decision | 정할 것 / 결정 |
| Must / Should / Could | 필수 / 권장 / 선택 |
| Traceability matrix | 추적표 (데이터에만) |
| Wording / Copy | 문구 |

### 8.5 산출물과 HTML의 구성

빌드는 사람용 HTML, AI용 `model.json`, 검사용 `report.json`을 만든다 (산출물 명세 3장). 사람용 HTML은 부분마다 한 파일이고 위쪽 탭으로 오간다. 첫 파일은 모델 데이터도 품어서, HTML만 넘겨도 AI와 어댑터가 전부 읽을 수 있다. 층은 네 가지다.

| 층 | 내용 | 누가 읽나 |
|---|---|---|
| 본문 | 8.1절의 네 부분. 한글 이름만 보인다 | 사람 |
| 그림 | 전체 흐름·플로우차트 도화지와 상태 다이어그램을 파일 안 벡터 그림(SVG)으로 넣는다. 외부 파일을 참조하지 않는다. 겹침 하네스를 통과한 것만 나간다 | 사람, 이미지만 받는 도구 |
| 모델 데이터 | `model.json`과 같은 것을 파일 안 구조화 데이터 블록으로 넣는다. 문서 지도(`document`)가 어느 부분이 무엇을 그렸는지 알린다 | AI, 출력 도구 |
| 표식 | 본문 요소마다 내부 ID를 속성으로 붙이고, 파일 머리에 버전·품질 점수·착수 가능 여부를 둔다 | 출력 도구, 검증 |

- **출력 도구와 AI는 화면 모양이 아니라 모델 데이터를 읽는다.** 같은 HTML을 어느 도구로 옮겨도 내용이 같다.
- 내용은 스크립트 없이도 모두 보여야 한다. 도화지 확대·이동과 프롬프트 복사는 보조 수단이고, 막히면 원래 크기 그림과 스크롤로 본다.
- **프롬프트 복사** 단추는 HTML·`model.json` 경로와 읽는 법이 담긴 프롬프트를 만든다. 경로는 열린 위치에서 계산한다.

## 9. 출력 대상 가이드

출력 대상은 미리 정할 수 없다. 대신 **어떤 대상이든 지켜야 할 약속**과 **대상이 표현하지 못할 때의 대체 규칙**을 정한다. 모든 어댑터의 입력은 `model.json`(첫 HTML 안에도 같은 데이터)이다. 새 대상은 이 가이드를 따르는 어댑터 하나로 붙인다.

### 9.1 어댑터 약속

| # | 약속 | 내용 |
|---|---|---|
| 1 | 모델 데이터만 받는다 | 입력은 `model.json`이다. 문서 지도(`document`)로 사람 문서에 무엇이 보였는지 안다. 착수 가능 여부와 통과율을 함께 옮긴다. 착수 불가 문서도 옮길 수 있지만 표시를 지우지 않는다 |
| 2 | 매핑표를 가진다 | 모델 요소 → 대상 요소 대응을 문서로 둔다 (9.3절) |
| 3 | 표현 등급을 선언한다 | 대상이 표현할 수 있는 등급 (9.2절)을 먼저 확인하고 대체 규칙을 적용한다 |
| 4 | 이름은 보이고 ID는 숨긴다 | 사람에게 보이는 제목·노드 이름·이슈 제목은 한글 이름으로 쓴다. 모델 ID는 대상의 메타데이터나 매핑 파일에만 남긴다. 메타데이터가 없는 대상이면 본문 끝에 작게 표기한다 |
| 5 | 다시 실행해도 같다 | 매핑이 있으면 갱신하고 없으면 만든다. 모델에서 사라진 요소는 지우지 않고 "삭제됨"으로 표시한다 |
| 6 | 자기 영역만 고친다 | 지정한 페이지·섹션·보드 밖은 수정하지 않는다 |
| 7 | 사람의 수정을 먼저 확인한다 | 갱신 전에 대상 쪽에서 사람이 고친 곳이 있는지 비교한다. 있으면 덮어쓰지 않고 차이를 보고하고, 원천에 반영할지 묻는다 |
| 8 | 게시 후 검증한다 | 대상을 다시 읽어 요소 수를 대조한다 (화면 수, 상태 수, 완료 조건 수, 그림 수) |
| 9 | 외부 게시는 확인을 받는다 | 게시 전에 대상·범위를 사람에게 확인한다. 민감 정보(계정, 키, 개인정보)가 본문에 없는지 검사한다 |

### 9.2 표현 등급과 대체 규칙

| 등급 | 표현 능력 |
|---|---|
| L0 | 텍스트만 |
| L1 | 표 |
| L2 | 이미지 첨부 |
| L3 | 대상 고유의 도형·프레임·블록 |
| L4 | 상호작용 (탭, 펼침, 링크 이동) |

| 모델 요소 | 가장 좋은 표현 | 낮출 때 |
|---|---|---|
| 관계도·흐름도 | L3 고유 도형 | L2 이미지 → L1 표 (출발 / 행동 / 도착) |
| 동작 가능표 | L1 표 (색 칸) | L0 "사용자 유형 · 상태: 가능 여부" 목록 |
| 화면 상태 전환 | L4 탭 | L1 상태별 소제목 반복 |
| 요소 간 링크 | L4 이름을 누르면 이동 | L0 이름을 따옴표로 표기 ('항목 목록' 화면). 이름은 중복이 없어 검색으로 찾을 수 있다 |
| 출처·정할 것 배지 | L1 색 배지 | L0 `[가정]` `[정할 것: 완료된 항목을 수정할 수 있는가?]` 괄호 표기 |

### 9.3 대상 유형별 매핑

특정 도구가 아니라 도구 유형을 기준으로 정한다. 어떤 도구를 쓰든 그 도구가 속한 유형의 매핑을 따른다.

| 유형 | 어떤 도구인가 | 모델 → 대상 |
|---|---|---|
| 문서형 | 위키, 문서 편집 도구 | 문서 1개 → 페이지 1개 (또는 섹션별 하위 페이지). 그림 → 첨부 이미지. 표 → 표 |
| 디자인형 | 화면을 프레임 단위로 그리는 디자인 도구 | 페이지 플로우차트·화면 목록 → 화면 × 상태 × 폭마다 빈 프레임 1개. 프레임 이름은 "항목 목록 · 빈 화면 · 데스크탑". 문구 → 실제 문구 텍스트. 기능명세서 요약 → 도구의 주석 기능. 배치는 디자이너가 그린다. 프레임 ↔ ID는 매핑 파일에 둔다 |
| 화이트보드형 | 도형과 연결선을 자유롭게 놓는 보드 도구 | 전체 흐름·플로우차트(시나리오·기능·페이지)·상태 다이어그램 → 보드 1개씩, 서비스는 섹션. 도형에는 한글 이름만 쓴다 |
| 이슈형 | 이슈 트래커 | 요구사항 → 이슈. 완료 조건 → 체크리스트. 정할 것 → 담당자가 지정된 하위 이슈나 코멘트. 문서 링크 → 이슈 링크 |
| 표형 | 스프레드시트 | 동작 가능표·엣지 케이스·추적표·이벤트 명세 → 시트별 표 |

한 도구가 여러 유형을 겸하면 (예: 디자인과 화이트보드를 모두 지원) 유형별 매핑을 각각 적용한다.

### 9.4 새 대상을 붙일 때 확인할 것

1. 대상의 표현 등급은 무엇인가 (9.2절)
2. 대상에 요소를 만들고, 읽고, 갱신하는 수단이 있는가 (MCP, API, 파일 가져오기 중 무엇)
3. 대상 쪽에 모델 ID를 남길 자리가 있는가
4. 사람이 대상에서 고친 것을 감지할 수 있는가 (버전, 수정 시각, 내용 비교)
5. 지정 영역을 제한할 수 있는가
6. 게시 후 다시 읽어 검증할 수 있는가
7. 권한·보안 제약은 무엇인가 (보는 사람의 계정 필요 여부, 공개 범위)

1~6 중 하나라도 불가능하면 한 방향 "내보내기" 전용 어댑터로 등록하고, 갱신은 지원하지 않는다고 문서에 표시한다.

## 10. 근거와 방향

### 10.1 제품 기준서 (사람이 쓴다, 1장)

| 항목 | 내용 |
|---|---|
| 문제와 대상 | 제품이 해결하는 문제, 대상 고객 |
| 핵심 지표 | 핵심 1개 + 지켜야 할 지표 |
| 판단 원칙 | 충돌할 때 무엇을 우선하는가 (예: "입력 시간 단축 > 기능 수") |
| 하지 않는 것 | 제품 차원에서 하지 않는 것 |

모델은 이 기준서로 세 가지를 한다. 원칙과 어긋나는 기획에 경고하고, 선택지마다 원칙에 주는 영향을 적고, 과거 결정 기록을 참조해 이미 정한 것을 다시 묻지 않는다. 방향 자체는 정하지 않는다.

### 10.2 컨텍스트 사전 (자동 추출)

| 사전 | 원천 형식 (프로필에서 지정) | 쓰임 |
|---|---|---|
| 권한 | 권한 정의 파일, 스키마 enum | 동작 가능표의 행과 권한 키. 사전에 없는 키는 "신규 제안" |
| 상태 | 스키마 enum | 상태 전이 뼈대. 모든 상태값에 화면 표시가 있는지 검사 |
| API | GraphQL, OpenAPI, DB 스키마 | 데이터 항목마다 "있음 / 없음 / 신규 필요" 대조 → 백엔드 요청서 |
| 컴포넌트 | 디자인 시스템 컴포넌트 목록 | 화면 요소가 기존 컴포넌트로 만들어지는지 대조 |
| 이벤트 | 분석 이벤트 정의 | 지표 → 기존 이벤트 연결, 신규 이벤트 이름 생성 |
| 용어 | 용어 사전 | 문장 규칙, 휴리스틱 2 |

기획서는 만들 때 참조한 사전의 버전을 기록한다. 원천이 바뀌면 검사 단계에서 다시 확인하라고 알린다. 원천이 없는 제품이면 해당 사전을 건너뛰고, 관련 사실은 `가정`으로 남는다.

### 10.3 출처 표시

| 표시 | 뜻 |
|---|---|
| `코드` · `스키마` | 저장소에서 추출한 사실 |
| `문서` | 기획·API 문서의 절 번호 |
| `데이터` | 이벤트·문의·버그 건수 |
| `레퍼런스` | 외부 사례. URL과 확인 날짜 필수. "좋다" 대신 "조사한 N개 중 M개가 이 방식"으로 쓴다 |
| `결정` | 결정 기록 번호 |
| `가정` | 근거 없음 |

## 11. 플러그인 구성 (개념)

| 구성 | 역할 |
|---|---|
| 진행 스킬 1개 | 입구 선택, 단계 진행, 인터뷰. 단계별 지침과 검토 기준을 필요할 때만 읽는다 |
| 단계별 지침 | 4장 각 단계의 질문, 초안 작성 방법, 통과 기준 |
| 검토 기준 | 5장 전체. 휴리스틱 확인 질문, 예외 목록, 심각도 기준 |
| 출력 가이드 | 9장 전체. 대상 유형별 매핑표 |
| 검사·도출·렌더 | 관계 규칙 검사, 하네스(그림 겹침·엣지 케이스 누락), 화면·플로우차트·전체 흐름·엣지 케이스 도출, HTML 네 파일·`model.json` 렌더, 어댑터(계획) |
| 프로젝트 프로필 | 원천 위치·형식, 화면 폭, 화면 상태, 용어 사전, 이벤트 이름 규칙 (구성·사용자 유형·앱은 기획서마다 `spec.json`에 적는다) |

사용 흐름은 이렇게 된다. 명령은 하나이고, 모델이 대화 중에 알아서 켜지 않는다. 사람이 명령으로 부를 때만 돈다.

```
/yw-product-spec {요구사항}   요구사항만 → 새로 만들기
                              자료를 함께 주면 → 보완하기
                              기존 spec.json과 바꿀 내용 → 변경하기
```

세 입구 모두 같은 반복을 돈다. 사람 답이 필요 없는 이슈는 스스로 고치고, 답이 필요한 빈칸만 묻고, 검사 통과율 100%·착수 가능이 되면 HTML 네 파일과 `model.json`을 만들어 창으로 연다. 검토(`check`)와 빌드(`build`)는 그 반복 안에서 파이프라인이 돌린다. 출력 어댑터는 사용자가 대상을 정한 뒤에만 쓴다.

## 14. 검증 루프

### 14.1 기준을 잡는 방법

검증 기준을 머릿속으로 정하면 그 기준이 다시 주관이 된다. 그래서 기준은 **이미 일어난 사실**에서만 가져온다.

| 정답의 원천 | 알려 주는 것 |
|---|---|
| 과거 결함 | 실제로 비용을 치른 문제. 이미 끝난 기능에서 개발 도중 발견된 기획 문제 |
| 심은 결함 | 기계 규칙이 제대로 작동하는지. 통과한 기획서에 결함을 일부러 넣은 것 |
| 새어 나간 결함 | 기준에 무엇이 빠졌는지. 관문을 통과한 뒤 개발·QA·운영에서 나온 기획 문제 |

목표 수치는 미리 정하지 않는다. **첫 측정값을 기준선으로 두고, 기준선보다 나빠지는 변경만 막는다** (래칫). 측정 없이 정한 목표 숫자는 근거가 없기 때문이다.

### 14.2 세 개의 루프

| 루프 | 무엇을 검증하나 | 언제 도나 |
|---|---|---|
| A. 문서 루프 | 기획서 하나가 관문을 통과하는가 | 기획서를 만들거나 바꿀 때마다 |
| B. 도구 루프 | 파이프라인이 결함을 잘 잡는가 | 규칙·지침·질문을 바꿀 때마다 |
| C. 실사용 루프 | 기획서가 실제로 개발 비용을 줄였는가 | 기능 출시 후 |

C에서 찾은 새어 나간 결함은 A의 규칙과 B의 평가셋으로 돌아간다. 기준은 처음부터 완벽하게 만들지 않고, 실제 경험에서 늘어난다.

### 14.3 A. 문서 루프

순서는 검사 → 이슈 분류 → 허용된 것만 고치기 → 다시 검사다.

| 이슈 | 루프가 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| 파생물 누락 (흐름도, 추적표, 완료 조건 초안) | 다시 파생한다 | — |
| 기본값으로 채울 수 있는 화면 상태 | 기본값으로 채우고 "기본값"으로 표시한다 | — |
| 출처 충돌 | 정할 것으로 올린다 | 한쪽을 골라 해결하기 |
| 동작 가능표 빈칸 | 정할 것으로 올리고, 비슷한 칸을 참고안으로 보여 준다 | 칸을 채우기 |
| 휴리스틱·워크스루 이슈 | 수정안을 제안한다 | 수정안을 적용하기 |

- 루프는 통과하려고 사실을 만들지 않는다.
- 회차마다 확인한다: 전에 통과한 규칙이 다시 실패하지 않았는가 (회귀), `가정` 비율이 늘지 않았는가 (날조 감시).
- 멈추는 조건:
  1. 관문을 통과했다.
  2. 한 회차에서 위반 수가 줄지 않았다.
  3. 남은 이슈가 모두 사람의 결정을 필요로 한다.
  4. 최대 회차 (기본 3회)에 도달했다.

### 14.4 B. 도구 루프

**평가셋 두 가지**

| 평가셋 | 만드는 법 | 쓰임 |
|---|---|---|
| 과거 결함셋 | 끝난 기능의 "착수 시점 입력"과 "개발 중 발견된 결함"을 쌍으로 만든다. 결함마다 유형 (14.5절)과 잡았어야 할 규칙을 표시한다 | 실제 문제를 잡는지 |
| 심은 결함셋 | 통과한 기획서에 결함 종류마다 몇 개씩 넣는다: 상태 삭제, 동작 가능표 칸 비우기, 화면 이동 끊기, 출처를 바꿔 충돌 만들기, 실패 처리 삭제, 용어 바꿔치기, 이름 중복 | 기계 규칙이 작동하는지. 과거 이력이 없는 새 도메인에서도 만들 수 있다 |

첫 과거 결함셋은 이미 개발이 끝난 기능 하나로 만든다. 조건은 두 가지다.

- **착수 시점 판본이 있어야 한다.** 기획 문서·시안·API 문서의 착수 당시 판본을 버전 이력에서 가져올 수 있어야 한다. 지금 판본에는 개발 중 결정이 이미 섞여 있어 평가가 왜곡된다.
- **개발 중 발견된 결함 기록이 있어야 한다.** 착수 후 기획 확인 질문, 시안 정합 수정, 착수 후 티켓에 추가된 명세, 원복 기록 등이다. 이 기록을 중복 제거하고 결함마다 유형과 잡았어야 할 규칙을 표시한다.

부록 A는 이런 결함이 흔히 어떤 모양인지와 어느 규칙이 잡는지를 보여 주는 예다.

**지표**

| 지표 | 계산 | 통과 기준 |
|---|---|---|
| 재현율 | 잡은 결함 / 평가셋의 결함 | 기계 규칙이 대상인 심은 결함: 100% (못 잡으면 규칙 버그). 과거 결함: 기준선 이상 |
| 정밀도 | 사람이 "진짜 문제"로 판정한 이슈 / 제기된 이슈 (심각도 3~4 기준) | 기준선 이상 |
| 결정성 | 같은 입력을 반복했을 때 기계 판정과 HTML이 같은가 | 100% |
| 판단 일관성 | 같은 입력을 3회 돌렸을 때 모델 판단 이슈가 겹치는 비율 | 기준선 이상. 많이 흔들리는 질문은 더 구체적으로 고친다 |
| 무날조 | 루프가 추가한 문장 중 출처도 `가정` 표시도 없는 것 | 0 |
| 입구 수렴 | 같은 기능을 새로 만들기와 보완하기로 각각 만들었을 때 품질 점수 차이 | 기준선 이하 |
| 흐름 수정률 | 사람이 바꾼 화면·이동 / 자동 도출한 화면·이동 (4.1절). 규칙별로도 잰다 | 기준선 이하 |

규칙·지침을 바꿀 때마다 B를 돌린다. 지표 하나라도 기준선보다 나빠지면 그 변경을 되돌린다.

주관이 남는 곳은 정밀도 판정 하나다 ("이 이슈가 진짜 문제인가"). 두 사람이 따로 판정해 일치율을 기록하고, 서로 다르게 본 이슈는 결정 기록으로 남긴다.

### 14.5 C. 실사용 루프

새어 나간 결함은 기획서가 관문을 통과한 뒤 개발·QA·운영에서 발견된 기획 문제다. 수집 신호는 프로필에서 원천을 지정한다: 착수 후 기획 확인 질문, 시안에 맞추려는 수정, 착수 후 티켓에 추가된 명세, 원복, 기획이 원인인 긴급 수정.

| 유형 | 뜻 | 잡았어야 할 곳 | 고치는 방법 |
|---|---|---|---|
| 누락 | 요소나 관계가 없었다 | 관계 규칙, 예외 목록 | 관계 규칙 또는 예외 항목 추가 |
| 충돌 | 출처끼리 달랐다 | 대조 | 대조 대상 원천 추가 |
| 모호 | 두 가지로 읽혔다 | 문장 규칙 | 금지 표현 추가 |
| 오류 | 규칙 내용이 틀렸다 | 사람의 결정 | 도구 범위 밖으로 기록 |
| 기술적 불가 | 만들 수 없었다 | 컨텍스트 사전 대조 | 사전 추출 범위 확대 |
| 사용성 | 사용자가 헤맸다 | 휴리스틱, 워크스루 | 확인 질문을 구체화 |

처리 순서: 결함 1건 → 유형 분류 → 규칙·질문·예외 목록 수정 → 그 사례를 과거 결함셋에 추가 → B를 다시 돌려 기준선 확인.

C의 성과 지표는 **기능당 새어 나간 결함 수 (유형별)**다. 기준선은 P2 파일럿 기능에서 잰다.

### 14.6 기준의 출처

| 기준 | 어디서 왔나 | 성격 |
|---|---|---|
| 관계 규칙 | 모델 정의 (3.2절) | 정의상 참 |
| 휴리스틱·워크스루 질문 | Nielsen 10, 인지적 워크스루 | 검증된 방법 |
| 재현율 기준 | 과거 결함, 심은 결함 | 사실 |
| 목표 수치 | 첫 측정 기준선 | 측정값 |
| 새 규칙 | 새어 나간 결함 | 사실 |

## 부록 A. 개발 도중 흔히 발견되는 기획 결함과 잡는 규칙

실제 프로젝트에서 개발이 시작된 뒤에 발견된 결함을 도메인 없이 일반화했다. 과거 결함셋 (14.4절)을 만들 때 분류 예시로 쓴다.

| 개발 중 발견되는 결함 | 잡는 규칙 |
|---|---|
| 항목 기간이 상위 기간을 넘어도 되는지 기획 문서의 두 절과 API가 서로 다름 | 7.2절 대조: 출처 충돌 |
| 상태 정의가 한 문서 안에 두 벌 있음 (구버전 본문이 남음) | 7.2절 대조 + 10.2절 상태 사전 |
| 기획서에는 수정 가능한 필드가 API에는 없음 | 10.2절 API 대조 → 백엔드 요청서 |
| "완료된 항목을 수정할 수 있는가"가 착수 후 티켓에서 정해짐 | 5.1절 동작 가능표 빈칸 |
| 새 기능의 권한이 기획서 권한 표에 없음 | 10.2절 권한 사전 vs 동작 가능표 행 |
| 관리자의 "확인" 처리를 어떤 동작이 일으키는지 불명 | 5.1절 상태 → 들어오는 전이 (트리거 동작 없음) |
| 사용자 앱 쪽 노출·완료 조건이 문서마다 다름 | 5.1절 교차 앱 → 받는 쪽 + 7.2절 대조 |
| 목록 0건 화면이 미정 | 5.1절 화면 상태 누락 |
| 불러오는 중 상태의 시안이 없음 | 5.1절 화면 상태 누락 → 4장 단계 8 시안 대조 |
| 여러 대상에게 한 번에 처리한 뒤 알림의 "보기" 버튼이 어디로 가는지 미정 | 5.4절 워크스루 질문 4 |
| 사유 입력이 최소 글자 수 미만일 때 버튼을 잠글지 미정 | 5.3절 휴리스틱 5 (막는 시점) |
| 등록한 링크를 수정하는 버튼이 시안에 없음 | 5.3절 휴리스틱 3 |
| 성공·실패 알림 문구가 미정 | 5.3절 휴리스틱 1·9 |
| 관리자 쪽과 사용자 쪽이 같은 개념을 다른 말로 부름 | 5.3절 휴리스틱 2 + 8.3절 용어 사전 |
