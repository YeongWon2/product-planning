# 산출물 명세

> 기획서 하나를 만들면 **무엇이 나와야 하는가**를 정한다. 구현은 이 명세를 계약으로 삼는다.
> 설계 배경은 [설계서](설계서.md)를 본다.

---

## 1. 무엇이 나오나

기획서 하나는 폴더 하나다.

```
{기능}/
├─ spec.json                 원천. 사람이 적은 사실만 담는다 (2장)
└─ out/
   ├─ {기능}.html             사람용 1 · PRD (+ AI용 모델 데이터를 품는다)
   ├─ {기능}.scenarios.html   사람용 2 · 시나리오
   ├─ {기능}.flowcharts.html  사람용 3 · 플로우차트 (화면 전체 도화지)
   ├─ {기능}.spec.html        사람용 4 · 기능명세서
   ├─ model.json             AI용 모델 데이터 (3.3절)
   └─ report.json            검사 결과 (4장)
```

| 산출물 | 누가 만드나 | 누가 읽나 | 사람이 고치나 |
|---|---|---|---|
| `spec.json` | 사람 (`/yw-product-spec`과 대화하며) | 파이프라인 | 예. 유일하게 고치는 파일 |
| HTML 네 파일 | 빌드 | 기획자·개발자·디자이너 | 아니오. 매번 다시 만든다 |
| `model.json` | 빌드 | AI·출력 어댑터 | 아니오 |
| `report.json` | 검사 | 자동화·스킬 | 아니오 |

**결정성 약속**: 같은 `spec.json`이면 모든 산출물은 바이트 단위로 같다. 빌드 시각이나 실행 위치 같은 값을 넣지 않는다. 프롬프트 복사 단추의 경로도 HTML이 열릴 때 계산한다.

## 2. 원천 `spec.json`

사람이 적는 것만 담는다. 화면·이동·플로우차트·엣지 케이스·완료 조건 초안·정할 것 일부는 파생되므로 적지 않는다 (5장).

### 2.1 최상위

| 키 | 필수 | 내용 |
|---|---|---|
| `meta` | 예 | `title` (기획서 이름), `version`, `profile` (2.3절) |
| `product` | 권장 | 구성 (2.2절). 없으면 경고 (`product`) |
| `summary` | 예 | `problem` (사실 + 출처), `metrics` (지표 목록). `outOfScope`는 선택이고 데이터에만 남는다 |
| `wording` | 권장 | 공통 문구 9종 (2.2절). 빠지면 경고 (`wording`) |
| `userTypes` | 예 | 사용자 유형 |
| `apps` | 예 | 사용자가 만나는 앱 |
| `requirements` | 예 | 요구사항 |
| `entities` | 예 | 개체와 상태, 전이 |
| `actions` | 예 | 동작 |
| `permissions` | 예 | 동작 가능표의 칸 |
| `scenarios` | 예 | 시나리오와 단계 |
| `acceptance` | 아니오 | 사람이 확정한 완료 조건 |
| `events` | 아니오 | 측정 이벤트 |
| `questions` | 아니오 | 사람이 적은 정할 것 |
| `decisions` | 아니오 | 결정 기록 |
| `flowOverrides` | 아니오 | 자동 흐름에서 사람이 바꾼 곳 |
| `reviews` | 권장 | 모델 판단(휴리스틱·워크스루)의 최종 결과. 없으면 경고 (`review-coverage`) |
| `reviewRounds` | 권장 | 독립된 두 번의 판단 `[첫째, 둘째]`. 일치율 계산에 쓴다 (`review-agreement`) |

모든 요소는 `id` (바뀌지 않는 연결 키)와 `name` (사람에게 보이는 한글 이름)을 가진다. ID 형식은 자유지만 요소 전체에서 겹치면 안 된다.

- "필수 = 예"인 목록 (`userTypes` · `apps` · `requirements` · `entities` · `actions` · `scenarios`)과 `summary.metrics`가 비어 있으면 착수 불가다 (`required`). 시나리오에는 단계가 1개 이상 있어야 한다 (`scenario-steps`).
- 형식이 틀린 값 (목록 자리에 문자열, 허용되지 않은 값 등)은 버리지만 조용히 버리지 않는다. 경로와 함께 형식 오류 (`shape`) 차단 이슈로 보고한다.
- 같은 ID가 여러 번 나오면 먼저 나온 것만 쓰고 ID 중복 (`id-duplicate`) 차단 이슈를 낸다.

### 2.2 요소별 필드

| 요소 | 필드 |
|---|---|
| 구성 `product` | `kind`: `service` (새 서비스) · `feature` (기존 서비스에 기능 추가) · `project` (기간이 정해진 프로젝트), `systems`: [`id`, `name`, `kind`: `service` · `api` · `external`, `apps` (서비스에 속한 앱 ID)] |
| 공통 문구 `wording` | `inputError` 입력 오류 · `denied` 권한 없음 · `empty` 빈 화면 · `loadError` 불러오기 오류 · `network` 통신 실패 · `unknown` 알 수 없는 오류 · `sessionExpired` 로그인 만료 · `confirmOk` 확인 단추 · `confirmCancel` 취소 단추 |
| 출처 `source` | `kind`: `code` · `schema` · `doc` · `data` · `reference` · `decision` · `assumption`, `ref`: 근거 위치 ("문서 이름 · 번호 제목"). 없으면 `assumption`으로 본다 |
| 사용자 유형 | `id`, `name`, `goal`, `source`, `automatic?` (사람이 아닌 자동 처리 주체. 기한 도래처럼 규칙으로 일어나는 단계를 맡는다) |
| 앱 | `id`, `name`, `platform`: `web` · `ios` · `android` · `desktop` · `mobile-web` 중 하나나 그 목록 |
| 요구사항 | `id`, `name`, `userType`, `priority`: `must` · `should` · `could`, `source` |
| 개체 | `id`, `name`, `states`: [`id`, `name`, `initial?`, `terminal?`], `transitions`: [`from`, `to`, `action`] |
| 동작 | `id`, `name`, `entity`, `kind`: `list` · `view` · `create` · `update` · `delete` · `other`, `inputs` (아래 입력), `async` (서버를 거침), `irreversible` (되돌릴 수 없음), `calls` (부르는 API 서버·외부 시스템 ID), `success` (성공 문구), `failures`: [`name`, `message`], `confirm`: {`message`, `ok?`, `cancel?`} (되돌릴 수 없는 동작이면 필수), `denied?` (권한 없음 문구, 공통 문구를 덮어씀), `empty?` (빈 화면 문구, 목록·상세), `crossApp`: [`app`, `userType`, `effect`, `message` (알림 문구)] |
| 입력 | `name`, `type`: `text` · `number` · `date` · `period` · `select` · `multiSelect` · `file` · `url` · `boolean`, `required?`, `min?`/`max?` (글자 수·값·개수. 날짜·기간은 '오늘'·'1개월' 같은 글도 된다), `options?` (고를 목록), `optionsFrom?` (목록을 가져올 곳), `maxCount?`/`maxSizeMB?`/`totalSizeMB?`/`formats?` (파일), `rules?` (형식으로 못 적는 추가 조건), `error?` (오류 문구, 공통 문구를 덮어씀), `note?` (동작 설명, 검증 아님) |
| 동작 가능표 칸 | `userType`, `action`, `state`, `value`: `allow` · `hide` · `disable` · `deny` |
| 시나리오 | `id`, `name`, `requirement`, `kind`: `main` · `alt` · `exception`, `steps`: [`userType`, `app`, `action`, `text`] |
| 완료 조건 | `id`, `requirement`, `situation`, `action`, `result`, `source` |
| 지표 | `id`, `name`, `events`: 이벤트 ID 목록, `source` |
| 이벤트 | `id`, `name`, `action` |
| 정할 것 | `id`, `name` (질문 문장), `owner`, `blocking` |
| 결정 | `id`, `name` (결정 문장), `source` |
| 흐름 바꾸기 | `action`, `as`: `screen` · `modal`, `decision` (결정 ID) |
| 판단 `reviews[]` | `key` (검토지 항목, 예 `H5:AC3`, `W:S1#2`), `verdict`: `pass` · `issue` · `na`, `severity` (issue면 1~4), `evidence` (근거 요소·화면 ID, 1개 이상), `finding`, `fix?`, `accepted?` (심각도 3~4를 받아들인 결정 ID) |

동작 가능표 칸은 **개체에 상태가 있을 때** 사용자 유형 × 동작 × 상태마다 하나다. 상태가 없는 개체는 `state`를 생략하고 사용자 유형 × 동작마다 하나다. `list`(목록 보기)와 `create`(만들기)는 개체에 상태가 있어도 `state`를 생략하고 사용자 유형마다 한 칸이다. 만들기 전에는 상태가 없고, 목록은 여러 상태를 함께 보여 주기 때문이다.

### 2.3 프로필 `meta.profile`

| 키 | 기본값 | 쓰임 |
|---|---|---|
| `modalMaxInputs` | 3 | 흐름 규칙 F3·F4의 기준 |
| `screenStates` | 불러오는 중, 빈 화면, 오류, 권한 없음, 보기 전용 | 목록·상세 화면이 갖춰야 할 상태. 엣지 케이스와 공통 규칙에 쓰인다 |
| `defaultOwner` | 기획 | 자동으로 만든 정할 것의 담당자 |

프로필 값의 형식이 틀리면 기본값을 쓰고 형식 오류로 보고한다.

## 3. 사람이 읽는 문서와 AI가 읽는 데이터

사람용 HTML은 **이것만 보고 개발할 수 있을 만큼만** 담고, 같은 사실을 두 번 쓰지 않는다. 나머지는 모두 `model.json`에 있다. 네 파일은 위쪽 탭으로 오가고, **프롬프트 복사** 단추는 첫 HTML과 `model.json`의 경로와 읽는 법이 담긴 프롬프트를 복사한다.

### 3.1 네 부분

| # | 파일 | 형태 | 담는 것 |
|---|---|---|---|
| 1 | PRD `{기능}.html` | 글·표 | 구성(구분, 서비스·앱·플랫폼, API), 해결할 문제(출처), 대상 사용자와 목표, 목표 지표(측정 이벤트), 요구사항(우선순위·누가). 이것뿐이다 |
| 2 | 시나리오 | 글 | 요구사항마다 시나리오 한 줄(이름·종류·누가·단계 수, 플로우차트로 가는 링크)과 확정된 완료 조건(상황·행동·결과). 단계 글은 플로우차트에만 있다 |
| 3 | 플로우차트 | 그림 (화면 전체 도화지) | 맨 위 **전체 흐름** 한 장, 그 아래 **시나리오**·**기능**·**페이지**마다 한 장 (설계서 4.2절). 확대·이동·전체 화면·프레임 바로가기 |
| 4 | 기능명세서 | 표·글·그림 | 맨 위 **공통 규칙**과 **공통 문구**를 한 번. **서비스마다** 나누고(함께 쓰는 기능은 양쪽에 두되 '누가'에는 그 서비스 사용자만), 개체마다 상태 다이어그램, 기능마다 **누가 · 넣는 것 · 결과 · 막는 경우** |

기능명세서의 한 기능:

| 칸 | 담는 것 |
|---|---|
| 누가 (제목 옆) | 사용자 유형마다 가능·숨김·비활성. 상태에 따라 다르면 상태별. 모든 상태에서 불가인 사용자는 적지 않는다 (공통 규칙에 "누가에 없는 사용자는 할 수 없음") |
| 넣는 것 (표) | 항목 · 형식 · 필수 · 범위·조건, 기능이 덮어쓴 오류 문구 |
| 결과 | 확인 창 문구와 단추, 빈 화면·권한 없음 문구(덮어쓴 것만), 성공·실패 문구(공통 문구와 같은 실패는 빼고), 상태 변화, 다른 앱 영향과 알림 문구 |
| 막는 경우 (한 줄) | 서로 다른 원인만: 입력 규칙 위반, 할 수 있는 사람도 막히는 상태, 확인 창 취소, 기능 고유의 실패 |

착수를 막는 것이 남아 있으면 첫 파일 맨 위에 "착수 전에 정할 것"으로 알린다. 내부 ID는 어디에도 보이지 않는다.

### 3.2 무엇을 글로, 무엇을 그림으로

| 형태 | 담는 것 | 이유 |
|---|---|---|
| 그림 | 순서와 갈래(플로우차트), 상태 변화(상태 다이어그램), 서비스 사이 연결(전체 흐름) | 흐름은 글로 읽으면 놓친다 |
| 표 | 요구사항, 입력 검증, 완료 조건 | 값은 표에서 찾는다 |
| 글 | 문제, 사용자, 지표, 권한, 문구, 막는 경우 | 짧은 문장이 가장 빠르다 |
| 데이터만 | 화면 목록·이동, 경계값 하나하나, 완료 조건 초안, 검사 세부와 품질 점수, 결정·정할 것 기록, 이번에 하지 않는 것 | 개발에 바로 필요하지 않다. `model.json`에서 읽는다 |

모든 기능에 같은 규칙과 문구는 기능명세서 맨 위에 한 번만 적고, 기능마다 되풀이하지 않는다.

### 3.3 모델 데이터 구조 (`model.json`)

```json
{

  "document": { "parts": [{ "key": "prd|scenarios|flowcharts|spec", "title": "", "shows": ["이 부분이 그린 데이터 경로"] }], "dataOnly": ["문서에 없고 데이터에만 있는 경로"] },
  "spec":    { "...": "정규화한 spec.json (형식 오류로 버린 값은 빠지고 report에 남는다)" },
  "derived": {
    "screens":   [{ "id": "", "name": "", "app": "", "entity": "", "type": "screen|modal|confirm|notification", "rule": "F1", "reason": "", "states": [] }],
    "edges":     [{ "from": "", "to": "", "label": "", "rule": "F10" }],
    "stepScreens": { "시나리오ID#단계순번": "화면ID" },
    "entries":   ["진입 화면 ID"],
    "permissionCells": [{ "userType": "", "action": "", "state": "상태 ID 또는 null", "value": "allow|hide|disable|deny 또는 null" }],
    "permissionGaps": [{ "userType": "", "action": "", "state": "" }],
    "overrideResults": [{ "action": "", "result": "applied|not-form|no-inputs|no-opener|unused" }],
    "questions": [{ "id": "", "name": "", "owner": "", "blocking": true, "auto": true }],
    "acceptanceDrafts": [{ "requirement": "", "situation": "", "action": "", "result": "", "from": "permission|transition" }],
    "flowcharts": [{ "kind": "scenario|function|page", "of": "시나리오·동작·화면 ID", "requirement": "", "name": "", "app": "페이지만", "nodes": [{ "id": "", "type": "start|process|decision|message|state|end", "text": "" }], "edges": [{ "from": "", "to": "", "kind": "main|no|loop", "label": "예|아니오|실패 이름|다시 입력|다시 시도" }] }],
    "overview": { "services": [{ "id": "", "name": "", "apps": [{ "id": "", "name": "", "nodes": ["요구사항 ID 또는 app:앱ID"] }] }], "systems": [{ "id": "", "name": "", "kind": "api|external" }], "edges": [{ "from": "", "to": "", "kind": "order|cross|call", "label": "" }], "names": {}, "types": { "ID": "requirement|auto|app" } },
    "review": { "worksheet": [{ "key": "H5:AC3", "criterion": "H2|H5|H6|H8|H10|W", "criterionName": "", "question": "", "target": "", "targetName": "", "context": {} }], "agreement": { "total": 0, "agreed": 0, "ratio": 1, "disagreements": ["key"] } },
    "edgeCases": [{ "action": "", "category": "입력|권한|상태|확인 창|서버|화면|다른 앱|자동", "input": "입력 이름 또는 null", "given": "상황", "ok": true, "expect": "기대 결과 (정해진 문구 포함)" }]

```

`derived.edgeCases`는 기능마다 개발자·QA가 확인할 경우의 전체 목록이다. 사람 문서에는 서로 다른 원인만 한 줄로 묶어 보이고, 경계값 하나하나는 여기에만 있다.

### 3.4 그림 약속 (하네스)

- 모든 그림은 그린 뒤 겹침을 검사한다: 상자 겹침, 선이 상자를 지남, 선이 포개짐, 선이 글자를 지남, 글자 겹침, 글자가 상자를 가림, 틀 겹침(틀 안의 틀은 허용).
- 겹치면 간격 배율을 1 → 1.25 → 1.5 → 2 → 2.5로 넓혀 다시 그린다. 그래도 남으면 빌드가 "그림 겹침 N건"으로 알린다.
- 옆으로 잇는 선은 위로 → 옆으로 → 아래로 꺾여 상자 위쪽이나 옆으로 들어간다. 한 상자의 같은 면에 붙는 선은 자리를 나눠 쓴다.
- 상자 글은 실제 폭(한글·영문·숫자·공백을 따로 센다)으로 줄을 바꿔 상자 안에 들어간다. 프레임은 제목·부제가 들어가게 넓힌다.
- 엣지 케이스가 어느 플로우차트에도 없으면 `flow-coverage` 경고를 낸다.

`test/layout-check.test.mjs`, `test/text-fit.test.mjs`, `test/coverage.test.mjs`가 이 약속을 확인한다.

### 3.5 표기 규칙

| 값 | 표기 |
|---|---|
| `allow` · `hide` · `disable` · `deny` | 가능 · 숨김 · 비활성 · 불가 |
| `must` · `should` · `could` | 필수 · 권장 · 선택 |
| `main` · `alt` · `exception` | 기본 흐름 · 대안 흐름 · 예외 흐름 |
| `service` · `feature` · `project` | 새 서비스 · 기존 서비스에 기능 추가 · 기간이 정해진 프로젝트 |
| 입력 형식 | 텍스트 · 숫자 · 날짜 · 기간 · 하나 선택 · 여러 개 선택 · 파일 · 링크 · 예/아니오 |
| 출처 위치 | 문서 기호 대신 장·절: `§3` → 3장, `§5.1.2` → 5.1.2절 |
| 조사 | 받침에 맞춘다 ('관리자가', '항목을', '사용자는') |

## 4. 검사 결과 `report.json`

```json
{
  "ready": false,
  "score": { "checked": 0, "passed": 0, "ratio": 0, "assumptionRatio": 0, "blockingQuestions": 0, "blockIssues": 0, "warnIssues": 0 },
  "reasons": ["착수를 막는 사유 (한글 문장)"],
  "issues": [{ "rule": "", "level": "block|warn", "message": "", "targets": [{ "id": "", "name": "" }] }]
}
```

- **착수 가능** (`ready: true`)은 차단 이슈 0, 착수를 막는 정할 것 0일 때만이다.
- **통과율 100%** (`score.ratio: 1`)는 경고까지 0건이라는 뜻이다. `/yw-product-spec`은 착수 가능이면서 통과율 100%일 때 멈춘다.
- `message`는 한글 문장이며 대상은 이름으로 부른다.

경고 규칙:

| 규칙 | 잡는 것 |
|---|---|
| `product` | 구분·시스템이 없음, 어느 서비스에도 속하지 않은 앱, 플랫폼 없는 앱, 시스템 목록에 없는 API를 부르는 동작 |
| `wording` | 공통 문구가 빠짐, 되돌릴 수 없는 동작에 확인 창 문구가 없음, 다른 앱 영향에 알림 문구가 없음 |
| `input-rule` | 형식(`type`)이 없는 입력, 목록(`options`·`optionsFrom`)이 없는 선택 입력 |
| `async-feedback` | 서버를 거치는 동작에 성공·실패 문구가 없음 |
| `requirement-priority` | 우선순위가 없거나 그 밖의 값인 요구사항 |
| `request-scope` | 어느 시나리오에서도 쓰이지 않는 동작, 동작이 없는 개체 (요청 밖이거나 시나리오가 빠짐) |
| `plain-text` | 사람이 읽는 글에 `§`·`¶`·`※` 같은 문서 기호가 있음 |
| `flow-coverage` | 엣지 케이스가 어느 플로우차트에도 그려지지 않음 (하네스) |
| `flow-override` | 흐름 바꾸기가 적용되지 않음 |
| `review-coverage` | 검토지 항목에 판단이 없음 |
| `review-evidence` | 근거가 없거나 기획서에 없는 요소를 근거로 듦, 검토지에 없는 항목 |
| `review-agreement` | 두 번 판단한 기록이 없거나 일치율이 80% 미만 (어긋난 항목을 알린다) |

차단 규칙 `review-severity`: 심각도 3~4 판단이 결정으로 받아들여지지 않고 남음 → 착수 불가.

검토지는 `node scripts/spec.mjs review <spec.json>`이 JSON으로 찍는다. 기준은 휴리스틱 2 사용자의 말(개체마다) · 5 오류 예방 시점(입력이 있는 동작마다) · 6 기억 부담(시나리오마다) · 8 필요한 것만(페이지마다) · 10 처음 사용 안내(목록 화면마다)와 인지적 워크스루 W1~W4(기본 흐름 단계마다)다. 기계로 판정하는 휴리스틱 1·3·4·7·9는 위 규칙들이 이미 잡는다.

## 5. 파생 규칙 요약

| 파생물 | 어디서 | 규칙 |
|---|---|---|
| 화면·이동 | 시나리오 단계, 동작, 흐름 바꾸기 | 설계서 4.1절 F1~F12 |
| 전체 흐름 | 요구사항, 시나리오 단계, 동작 가능표, 상태 전이, 다른 앱 영향, API 호출, 구성 | 설계서 4.2절 |
| 플로우차트 (시나리오·기능·페이지) | 시나리오 단계, 동작 가능표, 입력 형식, 되돌릴 수 없음, 실패 안내, 공통 문구, 상태 전이, 다른 앱 영향, 화면·이동 | 설계서 4.2절 FC0~FC4 |
| 엣지 케이스 | 입력 형식, 동작 가능표, 상태 전이, 되돌릴 수 없음, 실패 안내, 프로필 화면 상태, 다른 앱 영향, 자동 처리, 문구 | 설계서 4.3절 |
| 동작 가능표 빈칸 | 사용자 유형 × 동작 × 상태 | 칸이 없으면 빈칸 → 정할 것 |
| 정할 것 (자동) | 빈칸, 흐름 규칙으로 정할 수 없는 곳 | 담당자 = 프로필 `defaultOwner`, 착수를 막음 |
| 완료 조건 초안 (데이터만) | 가능이 아닌 칸, 상태 전이 | 칸: "'{사용자 유형}'가 '{상태}' 상태의 '{개체}'에 '{동작}'을 하려 하면 → 버튼이 보이지 않는다 / 눌리지 않는다 / 거절되고 이유가 안내된다". 전이: "'{개체}'가 '{상태}'일 때 '{동작}'을 하면 → '{다음 상태}'가 된다" |
