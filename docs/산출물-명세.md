# 산출물 명세

> 기획서 하나를 만들면 **무엇이 나와야 하는가**를 정한다. 구현은 이 명세를 계약으로 삼는다.
> 설계 배경은 [설계서](설계서.md)를 본다.

---

## 1. 무엇이 나오나

기획서 하나는 폴더 하나다.

```
{기능}/
├─ spec.json            원천. 사람이 적은 사실만 담는다 (§2)
└─ out/
   ├─ {기능}.html        정본. 사람이 읽고, 출력 도구가 읽는다 (§3)
   └─ report.json       검사 결과 (§4)
```

| 산출물 | 누가 만드나 | 사람이 고치나 |
|---|---|---|
| `spec.json` | 사람 (도구와 대화하며) | 예. 유일하게 고치는 파일 |
| `{기능}.html` | 빌드 | 아니오. 매번 다시 만든다 |
| `report.json` | 검사 | 아니오 |

**결정성 약속**: 같은 `spec.json`이면 `{기능}.html`과 `report.json`은 바이트 단위로 같다. 빌드 시각 같은 값을 넣지 않는다.

---

## 2. 원천 `spec.json`

사람이 적는 것만 담는다. 화면·이동·완료 조건 초안·정할 것 일부는 파생되므로 적지 않는다 (§5).

### 2.1 최상위

| 키 | 필수 | 내용 |
|---|---|---|
| `meta` | 예 | `title` (기획서 이름), `version`, `profile` (§2.3) |
| `summary` | 예 | `problem` (사실 + 출처), `outOfScope` (문자열 목록), `metrics` (지표 목록) |
| `userTypes` | 예 | 사용자 유형 |
| `apps` | 예 | 사용자가 만나는 앱 |
| `requirements` | 예 | 요구사항 |
| `entities` | 예 | 개체와 상태, 전이 |
| `actions` | 예 | 동작 |
| `permissions` | 예 | 동작 가능표의 칸 |
| `scenarios` | 예 | 시나리오와 단계 |
| `acceptance` | 아니오 | 사람이 확정한 완료 조건 |
| `events` | 아니오 | 측정 이벤트 |
| `questions` | 아니오 | 사람이 적은 정할 것 |
| `decisions` | 아니오 | 결정 기록 |
| `flowOverrides` | 아니오 | 자동 흐름에서 사람이 바꾼 곳 |

모든 요소는 `id` (바뀌지 않는 연결 키)와 `name` (사람에게 보이는 한글 이름)을 가진다. ID 형식은 자유지만 요소 전체에서 겹치면 안 된다.

### 2.2 요소별 필드

| 요소 | 필드 |
|---|---|
| 출처 `source` | `kind`: `code` · `schema` · `doc` · `data` · `reference` · `decision` · `assumption`, `ref`: 근거 위치 (문자열). 없으면 `assumption`으로 본다 |
| 사용자 유형 | `id`, `name`, `goal`, `source` |
| 앱 | `id`, `name` |
| 요구사항 | `id`, `name`, `userType`, `priority`: `must` · `should` · `could`, `source` |
| 개체 | `id`, `name`, `states`: [`id`, `name`, `initial?`, `terminal?`], `transitions`: [`from`, `to`, `action`] |
| 동작 | `id`, `name`, `entity`, `kind`: `list` · `view` · `create` · `update` · `delete` · `other`, `inputs`: [`name`, `rules`: 문자열 목록], `async`, `irreversible`, `success` (성공 안내 문구), `failures`: [`name`, `message`], `crossApp`: [`app`, `userType`, `effect`] |
| 동작 가능표 칸 | `userType`, `action`, `state`, `value`: `allow` · `hide` · `disable` · `deny` |
| 시나리오 | `id`, `name`, `requirement`, `kind`: `main` · `alt` · `exception`, `steps`: [`userType`, `app`, `action`, `text`] |
| 완료 조건 | `id`, `requirement`, `situation`, `action`, `result`, `source` |
| 지표 | `id`, `name`, `events`: 이벤트 ID 목록, `source` |
| 이벤트 | `id`, `name`, `action` |
| 정할 것 | `id`, `name` (질문 문장), `owner`, `blocking` |
| 결정 | `id`, `name` (결정 문장), `source` |
| 흐름 바꾸기 | `action`, `as`: `screen` · `modal`, `decision` (결정 ID) |

동작 가능표 칸은 **개체에 상태가 있을 때** 사용자 유형 × 동작 × 상태마다 하나다. 상태가 없는 개체는 `state`를 생략하고 사용자 유형 × 동작마다 하나다.

### 2.3 프로필 `meta.profile`

| 키 | 기본값 | 쓰임 |
|---|---|---|
| `modalMaxInputs` | 3 | 흐름 규칙 F3·F4의 기준 |
| `screenStates` | 불러오는 중, 빈 화면, 오류, 권한 없음, 보기 전용 | 화면마다 갖춰야 할 상태 |
| `defaultOwner` | 기획 | 자동으로 만든 정할 것의 담당자 |

## 3. 정본 `{기능}.html`

### 3.1 네 층

| 층 | 내용 | 조건 |
|---|---|---|
| 본문 | §3.2의 섹션 | 한글 이름만 보인다. 내부 ID는 본문 텍스트에 없다 (부록 제외) |
| 그림 | 화면 흐름도 (SVG) | 파일 안에 넣는다. 외부 파일·스크립트를 참조하지 않는다 |
| 모델 데이터 | `<script type="application/json" id="spec-model">` | §3.3 구조. 출력 도구는 이것만 읽는다 |
| 표식 | 요소마다 `data-spec-id`, `data-spec-kind` 속성. `<head>`에 `spec-version`, `spec-ready`, `spec-score` 메타 | 출력 도구와 검증이 읽는다 |

### 3.2 본문 섹션 (이 순서로 모두 있어야 한다)

| # | 섹션 | 반드시 보여 줄 것 |
|---|---|---|
| 1 | 요약 | 기획서 이름, 문제 (출처 배지), 목표 지표, 이번에 하지 않는 것, 품질 점수, **착수 가능 / 착수 불가**와 사유 |
| 2 | 사용자와 시나리오 | 사용자 유형 (목표), 시나리오별 단계. 단계마다 "어느 화면에서" |
| 3 | 개체와 상태 | 개체별 상태 목록과 전이 (어느 상태에서 → 어떤 동작으로 → 어느 상태로) |
| 4 | 동작 가능표 | 개체별 표. 행 = 사용자 유형 × 동작, 열 = 상태. 칸 = 허용 · 숨김 · 비활성 · 불가. 빈칸은 "정할 것"으로 표시 |
| 5 | 화면 흐름 | SVG 흐름도 + 같은 내용의 표 (출발 화면 / 행동 / 도착 화면 / 적용 규칙) |
| 6 | 화면 목록 | 화면마다 종류 (화면 · 모달 · 확인 창 · 알림), 앱, 적용 규칙과 이유, 화면 상태 목록 |
| 7 | 완료 조건 | 요구사항별 확정 완료 조건 (상황 → 행동 → 결과). 그 아래 자동 초안 (확인 필요 표시) |
| 8 | 지표와 이벤트 | 지표별 연결 이벤트 |
| 9 | 검토 결과 | 차단 이슈, 경고 이슈. 이슈마다 대상 이름과 규칙 |
| 10 | 정할 것과 결정 | 사람이 적은 것 + 자동으로 만든 것. 담당자, 착수를 막는지 |
| 11 | 부록: 추적표 | 요구사항 → 시나리오 → 화면 → 완료 조건. 여기서만 내부 ID를 보인다 |

### 3.3 모델 데이터 구조

```json
{
  "format": "product-planning/spec@1",
  "spec":    { "...": "spec.json 그대로" },
  "derived": {
    "screens":   [{ "id": "", "name": "", "app": "", "entity": "", "type": "screen|modal|confirm|notification", "rule": "F1", "reason": "", "states": [] }],
    "edges":     [{ "from": "", "to": "", "label": "", "rule": "F10" }],
    "stepScreens": { "시나리오ID#단계순번": "화면ID" },
    "permissionGaps": [{ "userType": "", "action": "", "state": "" }],
    "questions": [{ "id": "", "name": "", "owner": "", "blocking": true, "auto": true }],
    "acceptanceDrafts": [{ "requirement": "", "situation": "", "action": "", "result": "", "from": "permission|transition" }]
  },
  "report": { "...": "report.json 그대로" }
}
```

출력 도구 (디자인·화이트보드·문서·이슈 도구)는 `derived.screens`와 `derived.edges`로 화면과 흐름을 옮기고, 사람에게는 `name`을 보여 주며, `id`는 매핑에만 쓴다.

### 3.4 표기 규칙

| 값 | 표기 |
|---|---|
| `allow` · `hide` · `disable` · `deny` | 허용 · 숨김 · 비활성 · 불가 |
| `must` · `should` · `could` | 필수 · 권장 · 선택 |
| `main` · `alt` · `exception` | 기본 흐름 · 대안 흐름 · 예외 흐름 |
| `screen` · `modal` · `confirm` · `notification` | 화면 · 모달 · 확인 창 · 알림 |
| 출처 `code` … `assumption` | 코드 · 스키마 · 문서 · 데이터 · 레퍼런스 · 결정 · 가정 |
| 조사 | 받침에 맞춘다 ('관리자가', '항목을', '사용자는') |

## 4. 검사 결과 `report.json`

```json
{
  "ready": false,
  "score": { "checked": 0, "passed": 0, "ratio": 0, "assumptionRatio": 0, "blockingQuestions": 0, "blockIssues": 0, "warnIssues": 0 },
  "reasons": ["착수를 막는 사유 (한글 문장)"],
  "issues": [{ "rule": "", "level": "block|warn", "message": "", "targets": [{ "id": "", "name": "" }] }]
}
```

- **착수 가능** (`ready: true`)은 차단 이슈 0, 착수를 막는 정할 것 0일 때만이다.
- `message`는 한글 문장이며 대상은 이름으로 부른다.

## 5. 파생 규칙 요약

| 파생물 | 어디서 | 규칙 |
|---|---|---|
| 화면·이동 | 시나리오 단계, 동작, 흐름 바꾸기 | 설계서 §4.1 F1~F11 |
| 동작 가능표 빈칸 | 사용자 유형 × 동작 × 상태 | 칸이 없으면 빈칸 → 정할 것 |
| 정할 것 (자동) | 빈칸, 흐름 규칙으로 정할 수 없는 곳 | 담당자 = 프로필 `defaultOwner`, 착수를 막음 |
| 완료 조건 초안 | 허용이 아닌 칸, 상태 전이 | 칸: "'{사용자 유형}'가 '{상태}' 상태의 '{개체}'에 '{동작}'을 하려 하면 → 버튼이 보이지 않는다 / 눌리지 않는다 / 거절되고 이유가 안내된다". 전이: "'{개체}'가 '{상태}'일 때 '{동작}'을 하면 → '{다음 상태}'가 된다" |

| 구축 단계 | 이 명세에서 나오는 것 |
