# 산출물 명세

> 기획서 하나를 만들면 **무엇이 나와야 하는가**를 정한다. 구현은 이 명세를 계약으로 삼는다.
> 설계 배경은 [설계서](설계서.md)를 본다.

---

## 1. 무엇이 나오나

기획서 하나는 폴더 하나다.

```
{기능}/
├─ spec.json            원천. 사람이 적은 사실만 담는다 (2장)
└─ out/
   ├─ {기능}.html        정본. 사람이 읽고, 출력 도구가 읽는다 (3장)
   └─ report.json       검사 결과 (4장)
```

| 산출물 | 누가 만드나 | 사람이 고치나 |
|---|---|---|
| `spec.json` | 사람 (도구와 대화하며) | 예. 유일하게 고치는 파일 |
| `{기능}.html` | 빌드 | 아니오. 매번 다시 만든다 |
| `report.json` | 검사 | 아니오 |

**결정성 약속**: 같은 `spec.json`이면 `{기능}.html`과 `report.json`은 바이트 단위로 같다. 빌드 시각 같은 값을 넣지 않는다.

---

## 2. 원천 `spec.json`

사람이 적는 것만 담는다. 화면·이동·완료 조건 초안·정할 것 일부는 파생되므로 적지 않는다 (5장).

### 2.1 최상위

| 키 | 필수 | 내용 |
|---|---|---|
| `meta` | 예 | `title` (기획서 이름), `version`, `profile` (2.3절) |
| `summary` | 예 | `problem` (사실 + 출처), `metrics` (지표 목록). `outOfScope`는 선택 (데이터에만 남는다) |
| `product` | 권장 | 구성: `kind` (`service` 새 서비스 · `feature` 기존 서비스에 기능 추가 · `project` 프로젝트), `systems`: [`id`, `name`, `kind`: `service` · `api` · `external`, `apps` (서비스에 속한 앱 ID)]. 없거나 어느 서비스에도 속하지 않은 앱이 있으면 경고 (`product`) |
| `wording` | 권장 | 공통 문구: `inputError` `denied` `empty` `loadError` `network` `unknown` `sessionExpired` `confirmOk` `confirmCancel`. 없으면 경고 (`wording`) |
| `userTypes` | 예 | 사용자 유형 |
| `apps` | 예 | 사용자가 만나는 앱 |
| `requirements` | 예 | 요구사항 |
| `entities` | 예 | 개체와 상태, 전이 |
| `actions` | 예 | 동작 |
| `permissions` | 예 | 동작 가능표의 칸 |
| `scenarios` | 예 | 시나리오와 단계 |
| `acceptance` | 아니오 | 사람이 확정한 완료 조건 |
| `events` | 아니오 | 측정 이벤트 |
| `questions` | 아니오 | 사람이 적은 정할 것 |
| `decisions` | 아니오 | 결정 기록 |
| `flowOverrides` | 아니오 | 자동 흐름에서 사람이 바꾼 곳 |

모든 요소는 `id` (바뀌지 않는 연결 키)와 `name` (사람에게 보이는 한글 이름)을 가진다. ID 형식은 자유지만 요소 전체에서 겹치면 안 된다.

- "필수 = 예"인 목록 (`userTypes` · `apps` · `requirements` · `entities` · `actions` · `scenarios`)과 `summary.metrics`가 비어 있으면 착수 불가다 (`required`). 시나리오에는 단계가 1개 이상 있어야 한다 (`scenario-steps`).
- 형식이 틀린 값 (목록 자리에 문자열, true/false 자리에 문자열, 허용되지 않은 `flowOverrides.as` 등)은 버리지만 조용히 버리지 않는다. 경로와 함께 형식 오류 (`shape`) 차단 이슈로 보고한다.
- 같은 ID가 여러 번 나오면 먼저 나온 것만 쓰고 ID 중복 (`id-duplicate`) 차단 이슈를 낸다.

### 2.2 요소별 필드

| 요소 | 필드 |
|---|---|
| 출처 `source` | `kind`: `code` · `schema` · `doc` · `data` · `reference` · `decision` · `assumption`, `ref`: 근거 위치 (문자열). 없으면 `assumption`으로 본다 |
| 사용자 유형 | `id`, `name`, `goal`, `source`, `automatic?` (사람이 아닌 자동 처리 주체. 기한 도래처럼 규칙으로 일어나는 단계를 맡는다. 흐름 규칙 F12) |
| 앱 | `id`, `name`, `platform`: `web` · `ios` · `android` · `desktop` · `mobile-web` |
| 요구사항 | `id`, `name`, `userType`, `priority`: `must` · `should` · `could`, `source` |
| 개체 | `id`, `name`, `states`: [`id`, `name`, `initial?`, `terminal?`], `transitions`: [`from`, `to`, `action`] |
| 동작 | `id`, `name`, `entity`, `kind`: `list` · `view` · `create` · `update` · `delete` · `other`, `inputs` (아래 입력), `async`, `irreversible`, `success` (성공 문구), `failures`: [`name`, `message`], `confirm`: {`message`, `ok?`, `cancel?`} (되돌릴 수 없는 동작이면 필수), `calls?` (부르는 API 서버·외부 시스템 ID), `denied?` (권한 없음 문구, 공통 문구를 덮어씀), `empty?` (빈 화면 문구, 목록·상세), `crossApp`: [`app`, `userType`, `effect`, `message` (알림 문구)] |
| 입력 | `name`, `type`: `text` · `number` · `date` · `period` · `select` · `multiSelect` · `file` · `url` · `boolean`, `required?`, `min?`/`max?` (글자 수·값·개수, 날짜·기간은 '오늘'·'1개월' 같은 글도 됨), `options?` (고를 목록), `optionsFrom?` (목록을 가져올 곳), `maxCount?`/`maxSizeMB?`/`totalSizeMB?`/`formats?` (파일), `rules?` (형식으로 못 적는 추가 조건, 문자열 목록), `error?` (오류 문구, 공통 문구를 덮어씀), `note?` (동작 설명, 검증 아님). 형식이 없으면 경고 (`input-rule`) |
| 동작 가능표 칸 | `userType`, `action`, `state`, `value`: `allow` · `hide` · `disable` · `deny` |
| 시나리오 | `id`, `name`, `requirement`, `kind`: `main` · `alt` · `exception`, `steps`: [`userType`, `app`, `action`, `text`] |
| 완료 조건 | `id`, `requirement`, `situation`, `action`, `result`, `source` |
| 지표 | `id`, `name`, `events`: 이벤트 ID 목록, `source` |
| 이벤트 | `id`, `name`, `action` |
| 정할 것 | `id`, `name` (질문 문장), `owner`, `blocking` |
| 결정 | `id`, `name` (결정 문장), `source` |
| 흐름 바꾸기 | `action`, `as`: `screen` · `modal`, `decision` (결정 ID) |

동작 가능표 칸은 **개체에 상태가 있을 때** 사용자 유형 × 동작 × 상태마다 하나다. 상태가 없는 개체는 `state`를 생략하고 사용자 유형 × 동작마다 하나다.

`list`(목록 보기)와 `create`(만들기)는 개체에 상태가 있어도 `state`를 생략하고 사용자 유형마다 한 칸이다. 만들기 전에는 항목이 없어 상태가 없고, 목록은 여러 상태를 함께 보여 주기 때문이다. 목록에서 특정 상태만 보이게 하는 규칙은 동작이 아니라 화면 규칙으로 적는다.

### 2.3 프로필 `meta.profile`

| 키 | 기본값 | 쓰임 |
|---|---|---|
| `modalMaxInputs` | 3 | 흐름 규칙 F3·F4의 기준 |
| `screenStates` | 불러오는 중, 빈 화면, 오류, 권한 없음, 보기 전용 | 화면마다 갖춰야 할 상태 |
| `defaultOwner` | 기획 | 자동으로 만든 정할 것의 담당자 |

프로필 값의 형식이 틀리면 기본값을 쓰고 형식 오류로 보고한다.

## 3. 산출물

`build`는 `out/`에 세 파일을 만든다.

| 파일 | 누가 읽나 | 내용 |
|---|---|---|
| `{기능}.html` · `{기능}.scenarios.html` · `{기능}.flowcharts.html` · `{기능}.spec.html` | 사람 (기획자·개발자·디자이너) | 3.1절의 네 부분, 부분마다 한 파일이고 위쪽 탭으로 오간다. 이것만 보고 개발할 수 있어야 한다. 같은 내용을 두 번 쓰지 않는다 |
| `model.json` | AI·출력 도구 | 3.3절 구조. 사람 문서에 없는 것까지 모두 담는다. 첫 HTML 파일 안 `<script type="application/json" id="spec-model">`에도 같은 것이 있다 |
| `report.json` | 검사 | 4장 |

HTML 위쪽 **프롬프트 복사** 단추는 두 파일의 경로와 읽는 법이 담긴 프롬프트를 복사한다. 경로는 HTML이 열린 위치에서 계산하므로 파일을 옮겨도 맞다.

### 3.1 사람이 읽는 네 부분

| # | 부분 | 형태 | 담는 것 |
|---|---|---|---|
| 1 | PRD | 글·표 | 해결할 문제(출처), 대상 사용자와 목표, 목표 지표(측정 이벤트), 요구사항(우선순위·누가). 이것뿐이다 |
| 2 | 시나리오 | 글 | 요구사항마다 시나리오 한 줄(이름·종류·누가·단계 수, 플로우차트로 이어지는 링크)과 확정된 완료 조건(상황·행동·결과). 단계 글은 여기 없고 플로우차트에만 있다 |
| 3 | 플로우차트 | 그림 (도화지, 화면 전체) | 맨 위 전체 흐름 한 장(서비스 틀 안에 앱별 요구사항, 먼저 만들어야 쓸 수 있는 순서, 다른 서비스 영향, API 호출. 화면 단위 이동은 없다), 그 아래 시나리오마다·기능마다·페이지마다 한 장. 설계서 4.2절. 확대·이동·전체 화면·프레임 바로가기 |
| 4 | 기능명세서 | 표·글·그림 | **서비스마다** 나눈다(기능은 쓰이는 앱이 속한 서비스 아래, 함께 쓰면 양쪽에 두고 '누가'에는 그 서비스 사용자만). 맨 위 **공통 규칙**(숨김·비활성·불가의 뜻, 입력 오류 처리, 중복 요청, 화면 상태)과 **공통 문구**를 한 번. 개체마다 상태 다이어그램. 기능마다 제목 옆 **누가**(사용자 유형별 가능·숨김·불가, 상태가 다르면 상태별), **넣는 것** 표(항목·형식·필수·범위·조건, 덮어쓴 오류 문구), **결과**(확인 창 문구와 단추, 빈 화면·권한 없음 문구, 성공·실패 문구, 상태 변화, 다른 앱 알림 문구), **막는 경우** 한 줄(서로 다른 원인만) |

착수를 막는 것이 남아 있으면 맨 위에 "착수 전에 정할 것"으로 알린다. 내부 ID는 어디에도 보이지 않는다.

### 3.2 무엇을 글로, 무엇을 그림으로

| 형태 | 담는 것 | 이유 |
|---|---|---|
| 그림 | 순서와 갈래(플로우차트), 상태 변화(상태 다이어그램) | 흐름은 글로 읽으면 놓친다 |
| 표 | 권한, 입력 검증, 완료 조건, 요구사항 | 값은 표에서 찾는다 |
| 글 | 문제, 사용자, 지표, 문구, 막는 경우 | 짧은 문장이 가장 빠르다 |
| 데이터만 | 화면 목록·이동, 완료 조건 초안, 경계값 하나하나, 검사 세부, 결정·정할 것 기록, 추적표 | 개발에 바로 필요하지 않다. `model.json`에서 읽는다 |

같은 사실은 한 곳에만 둔다. 모든 기능에 같은 규칙과 문구는 기능명세서 맨 위에 한 번만 적고, 기능마다 되풀이하지 않는다.

### 3.3 모델 데이터 구조 (`model.json`)

```json
{
  "format": "product-planning/spec@1",
  "document": { "parts": [{ "key": "prd|scenarios|flowcharts|spec", "title": "", "shows": ["이 부분이 그린 데이터 경로"] }], "dataOnly": ["문서에 없고 데이터에만 있는 경로"] },
  "spec":    { "...": "정규화한 spec.json (형식 오류로 버린 값은 빠지고 report에 남는다)" },
  "derived": {
    "screens":   [{ "id": "", "name": "", "app": "", "entity": "", "type": "screen|modal|confirm|notification", "rule": "F1", "reason": "", "states": [] }],
    "edges":     [{ "from": "", "to": "", "label": "", "rule": "F10" }],
    "stepScreens": { "시나리오ID#단계순번": "화면ID" },
    "entries":   ["진입 화면 ID (시나리오 첫 화면, 알림)"],
    "permissionCells": [{ "userType": "", "action": "", "state": "상태 ID 또는 null", "value": "allow|hide|disable|deny 또는 null" }],
    "permissionGaps": [{ "userType": "", "action": "", "state": "" }],
    "overrideResults": [{ "action": "", "result": "applied|not-form|no-inputs|no-opener|unused" }],
    "questions": [{ "id": "", "name": "", "owner": "", "blocking": true, "auto": true }],
    "acceptanceDrafts": [{ "requirement": "", "situation": "", "action": "", "result": "", "from": "permission|transition" }],
    "flowcharts": [{ "kind": "scenario|function|page", "of": "시나리오·동작·화면 ID", "requirement": "", "name": "", "app": "페이지만", "nodes": [{ "id": "", "type": "start|process|decision|message|state|end", "text": "" }], "edges": [{ "from": "", "to": "", "kind": "main|no|loop", "label": "예|아니오|실패 이름|다시 입력|다시 시도" }] }],
    "overview": { "services": [{ "id": "", "name": "", "apps": [{ "id": "", "name": "", "nodes": ["요구사항 ID 또는 app:앱ID"] }] }], "systems": [{ "id": "", "name": "", "kind": "api|external" }], "edges": [{ "from": "", "to": "", "kind": "order|cross|call", "label": "" }], "names": {}, "types": { "ID": "requirement|auto|app" } },
    "edgeCases": [{ "action": "", "category": "입력|권한|상태|확인 창|서버|화면|다른 앱|자동", "input": "입력 이름 또는 null", "given": "상황", "ok": true, "expect": "기대 결과 (정해진 문구 포함)" }]
  },
  "report": { "...": "report.json 그대로" }
}
```

`derived.edgeCases`는 기능마다 개발자·QA가 확인할 경우의 전체 목록이다. 사람 문서에는 서로 다른 원인만 한 줄로 요약해 보이고, 경계값 하나하나는 여기에만 있다.

### 3.4 표기 규칙

| 값 | 표기 |
|---|---|
| `allow` · `hide` · `disable` · `deny` | 허용 · 숨김 · 비활성 · 불가 |
| `must` · `should` · `could` | 필수 · 권장 · 선택 |
| `main` · `alt` · `exception` | 기본 흐름 · 대안 흐름 · 예외 흐름 |
| `screen` · `modal` · `confirm` · `notification` | 화면 · 모달 · 확인 창 · 알림 |
| 출처 `code` … `assumption` | 코드 · 스키마 · 문서 · 데이터 · 레퍼런스 · 결정 · 가정 |
| 조사 | 받침에 맞춘다 ('관리자가', '항목을', '사용자는') |
| 입력 형식 | 텍스트 · 숫자 · 날짜 · 기간 · 하나 선택 · 여러 개 선택 · 파일 · 링크 · 예/아니오 |

## 4. 검사 결과 `report.json`

```json
{
  "ready": false,
  "score": { "checked": 0, "passed": 0, "ratio": 0, "assumptionRatio": 0, "blockingQuestions": 0, "blockIssues": 0, "warnIssues": 0 },
  "reasons": ["착수를 막는 사유 (한글 문장)"],
  "issues": [{ "rule": "", "level": "block|warn", "message": "", "targets": [{ "id": "", "name": "" }] }]
}
```

- **착수 가능** (`ready: true`)은 차단 이슈 0, 착수를 막는 정할 것 0일 때만이다.
- **통과율 100%** (`score.ratio: 1`)는 경고까지 0건이라는 뜻이다. 명령 `/yw-product-spec`은 착수 가능이면서 통과율 100%일 때 멈춘다.
- 경고 `flow-coverage`: 엣지 케이스가 어느 플로우차트에도 그려지지 않은 곳 (하네스).
- 경고 `product`: 구분·시스템이 없거나, 어느 서비스에도 속하지 않은 앱, 플랫폼 없는 앱, 시스템 목록에 없는 API를 부르는 동작.
- 경고 `wording`: 공통 문구가 빠졌거나, 되돌릴 수 없는 동작에 확인 창 문구가 없거나, 다른 앱 영향에 알림 문구가 없는 곳.
- 경고 `plain-text`: 사람이 읽는 글(이름·문구·규칙·결정·질문 등)에 `§`·`¶`·`※` 같은 문서 기호가 있는 곳. 출처 위치(`ref`)는 검사하지 않고, 화면에 보일 때 `3장`은 '3장', `5.1.2절`는 '5.1.2절'로 풀어 보여 준다.
- 경고 `requirement-priority`: 우선순위(`must`·`should`·`could`)가 없거나 그 밖의 값인 요구사항.
- 경고 `request-scope`: 어느 시나리오 단계에서도 쓰이지 않는 동작, 동작이 하나도 없는 개체. 요청 밖 요소이거나 시나리오가 빠진 것이다.
- `message`는 한글 문장이며 대상은 이름으로 부른다.

## 5. 파생 규칙 요약

| 파생물 | 어디서 | 규칙 |
|---|---|---|
| 화면·이동 | 시나리오 단계, 동작, 흐름 바꾸기 | 설계서 4.1절 F1~F12 |
| 플로우차트 (시나리오·기능·페이지) | 시나리오 단계, 동작 가능표, 입력 형식, 되돌릴 수 없음, 성공·실패 안내, 상태 전이, 다른 앱 영향, 화면·이동, 공통 문구 | 설계서 4.2절 |
| 엣지 케이스 | 입력 형식, 동작 가능표, 상태 전이, 되돌릴 수 없음, 실패 안내, 프로필 화면 상태, 다른 앱 영향, 자동 처리, 문구 | 설계서 4.3절 |
| 동작 가능표 빈칸 | 사용자 유형 × 동작 × 상태 | 칸이 없으면 빈칸 → 정할 것 |
| 정할 것 (자동) | 빈칸, 흐름 규칙으로 정할 수 없는 곳 | 담당자 = 프로필 `defaultOwner`, 착수를 막음 |
| 완료 조건 초안 | 허용이 아닌 칸, 상태 전이 | 칸: "'{사용자 유형}'가 '{상태}' 상태의 '{개체}'에 '{동작}'을 하려 하면 → 버튼이 보이지 않는다 / 눌리지 않는다 / 거절되고 이유가 안내된다". 전이: "'{개체}'가 '{상태}'일 때 '{동작}'을 하면 → '{다음 상태}'가 된다" |
