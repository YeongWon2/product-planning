# 설계서

> 작성일 2026-10-24 · v2.0 초안
> product-planning이 무엇을 만들고, 사람과 AI가 어떤 순서로 같이 쓰는지 정한다.
> 레포 문서(작성법·설계·스킬)는 200줄 이하로 쓴다. 결과 스펙 문서는 줄 수 제한이 없다.

---

## 0. 한 장 요약

| 항목 | 내용 |
|---|---|
| 만드는 것 | 기획 PRD, 기획 상세 스펙, 개발 스펙, 시퀀스 다이어그램 네 문서 |
| 남는 곳 | 대상 프로젝트의 `docs/product/{feature}/` (그 기능의 기준 문서) |
| 쓰는 사람 | 사람이 정하고, AI는 원문을 인용해 묻고 옮기고, 하네스는 검토한다 |
| 진행 방식 | 같이 작성 → 하네스 리뷰 → 질문 → 질문이 없으면 다음 단계 |
| 흐름 | 기획(`/yw-plan`)과 개발(`/yw-dev`)을 따로 두되, 기획 확정이 개발로 이어지는 한 흐름 |
| 참고한 것 | GitHub Spec Kit, Kiro, OpenSpec |
| 범위 밖 | 기술 컨벤션, 코드 규칙, 비주얼 디자인 (각 프로젝트 규칙을 따른다) |

## 1. 원칙

1. **AI는 자동으로 쓰지 않는다.** 사람이 답한 내용만 문서에 옮긴다.
2. **질문은 원문을 인용해 입력창으로 작게 한다.** 어느 문서 어느 줄에서 나온 질문인지 그대로 보이며 1~3개만 묻는다 (4장).
3. **단계를 건너뛰지 않는다.** 한 단계의 검토 결과가 0건이어야 다음 단계로 간다.
4. **빈칸은 비워 두고 묻는다.** 모르는 것은 `정할 것`에 남기며, 남아 있으면 확정할 수 없다.
5. **모든 항목은 근거를 가진다.** BR → R → 트리 → 계약 → 작업 → 검증으로 이어지며, 끊긴 곳은 하네스가 찾는다.
6. **기획과 개발을 섞지 않는다.** 기획은 비개발자 말로, 개발은 코드로 알 수 없는 것만 쓴다.
7. **한 사실은 한 곳에만 쓴다.** 다른 문서는 번호로 부르고, 결과물에서는 링크가 된다.
8. **확정은 사람만 한다.** `상태: 확정`은 사람이 말했을 때만 바꾼다.

## 3. 전체 흐름

```text
[기획 · /yw-plan]
  1. 비즈니스 요구사항 ─▶ 2. 기획 요구사항 ─▶ 3. PRD 확정 ─▶ 4. 기획 상세 스펙 확정
     brief.md              plan.md              (①)              spec.md (②)
                                                                      │
                                         "개발 스펙으로 넘어갈까요?" ◀─┘
[개발 · /yw-dev]                                                      ▼
  5. 개발 스펙 ─ 결정 → 아키텍처 → 데이터 → 계약 → 시퀀스 → 오류 → 제약 → 작업 → 검증 → 규칙 대조 → 확정
     dev.md (③) + diagram.md (④)
```

| 시작할 때 상태 | 하는 일 |
|---|---|
| 기획 폴더가 없다 | 1단계부터 기획을 시작한다 (`/yw-dev`로 시작해도 같다) |
| 기획이 `작성중`이다 | 하네스가 알려 주는 멈춘 단계부터 기획을 잇는다 |
| 기획이 모두 `확정`이다 | 개발 스펙 인터뷰를 시작한다 |
| `docs/product/{feature}/`가 이미 있다 | 결과 문서를 작업 폴더로 읽어 와 고친다 (새로 만들지 않는다) |

- 개발을 쓰다가 기획과 어긋나는 답이 나오면 개발 문서에 쓰지 않고 `기획에 돌려보낼 것`에 남긴다.
- 기획을 고치면 그 문서가 `작성중`으로 돌아가고, 다시 확정해야 개발을 잇는다.
- 기획이 바뀌면 그 줄을 인용한 개발 항목은 하네스가 `[출처 낡음]`으로 알린다.

## 4. 질문 모양

질문마다 어디서 나온 질문인지 원문을 그대로 붙인다.

```text
근거  기획 상세 스펙 › F1 게시글 수정 › 예 › 게시됨
원문  "[저장] 누름 → 고친 글이 보이고 댓글은 그대로 남는다"
질문  저장할 때 화면은 무엇을 보내고, 성공하면 무엇을 돌려받나요?
```

- 원문은 고치거나 줄이지 않고 그대로 쓴다.
- 1단계처럼 앞선 문서가 없으면 사람이 한 말을 원문으로 인용해 확인한다.
- AI가 코드를 읽었으면 `근거 코드  경로:줄`을 더할 수 있지만, 코드에서 읽은 것을 답처럼 문서에 쓰지 않는다.
- 답을 옮길 때 `출처:` 줄에 근거를 함께 남기며, 원문이 바뀌면 하네스가 다시 묻게 한다.

## 5. 번호와 링크

| 번호 | 뜻 | 사는 곳 |
|---|---|---|
| `G1` `BR1` | 목표, 비즈니스 요구사항 | ① |
| `P1` `R1` `R1-1` | 페르소나, 요구사항, 완성 기준 | ① |
| `F1` `FN1` | 피쳐 트리, 함수 트리 | ② |
| `D1` `A1` `M1` `C1` `E1` `N1` `T1` `V1` | 결정, 구성 요소, 데이터, 계약, 오류, 제약, 작업, 검증 | ③ |
| `S1` | 시퀀스 | ④ |

- 작업 파일에는 번호만 쓰고, 내보낼 때 하네스가 `[R1](prd.md#r1)` 모양 링크로 바꾼다.
- 링크는 양쪽으로 건다. 번호가 쓰인 곳 아래에 하네스가 "이 항목을 쓰는 곳" 줄을 붙인다.
- 가리키는 번호가 없으면 `[깨진 링크]`, 어디서도 불리지 않으면 `[외톨이]`로 알린다.

## 6. 매 답의 루프

1. 사람이 답한다.
2. AI가 답을 해당 파일의 해당 칸에 출처와 함께 옮긴다.
3. AI가 `check`를 돌린다.
4. 걸린 것 가운데 사람 답이 필요한 것만 원문 인용 질문으로 바꿔 1~3개 묻는다.
5. 형식만 틀린 것(번호 순서, 표 모양)은 묻지 않고 고친 뒤 3으로 돌아간다.
6. 걸린 것이 없으면 다음 단계를 알리고 그 단계 첫 질문을 한다.

## 7. 하네스와 모델의 역할

| 일 | 하네스 | 모델 | 사람 |
|---|---|---|---|
| 문서 내용 정하기 | | | 한다 |
| 질문 만들기 | 걸린 것과 원문 줄을 알려 준다 | 원문을 인용해 사람 말로 묻는다 | |
| 답을 문서로 옮기기 | | 출처와 함께 옮긴다 | 확인한다 |
| 형식·근거·링크 검사 | 한다 | | |
| 요구사항 대조 | 근거 줄이 실제로 있는지 센다 | 기준마다 근거 줄을 찾는다 | 빠졌다고 나온 것에 답한다 |
| 결과물 내보내기 | 링크를 만들고 `docs/product/{feature}/`에 쓴다 | | 확정한다 |

## 8. 구성

| 위치 | 내용 |
|---|---|
| `scripts/pp.mjs` | 하네스 CLI |
| `src/` | 문서 읽기, 규칙, 대조, 보고, 내보내기 |
| `skills/yw-plan/` | 기획 1~4단계를 이끄는 스킬 |
| `skills/yw-dev/` | 개발 스펙과 다이어그램을 이끄는 스킬 |
| `examples/post-edit/` | 끝까지 통과한 예시 |

작업 폴더는 지금처럼 프로젝트 밖 `~/.product-planning/work/{feature}/`에 두고, 결과물만 프로젝트에 남긴다.

## 9. 이전 방식과 다른 점

- v1.0은 기획과 SDD 스펙 두 문서를 고른 폴더에 냈다.
- v2.0은 비즈니스 인터뷰를 앞에 더하고, 개발 스펙과 다이어그램을 뒤에 더해 네 문서를 낸다.
- "SDD 스펙"은 "기획 상세 스펙"으로 이름을 바꾼다.
- 결과물은 프로젝트 안 기준 문서가 되어, 다음 수정 때 다시 읽어 와 고친다 (OpenSpec 방식).
