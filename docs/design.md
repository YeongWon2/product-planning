# 설계서

> 작성일 2026-10-14 · v1.0
> product-planning이 무엇을 만들고, 사람과 AI가 어떤 순서로 같이 쓰는지 정한다.
> 문서는 모두 200줄 이하로 쓴다.

---

## 0. 한 장 요약

| 항목 | 내용 |
|---|---|
| 만드는 것 | 기획(비개발자용)과 SDD 스펙(개발자용) 두 문서 |
| 쓰는 사람 | 사람이 정하고, AI는 묻고 옮기고, 하네스는 검토한다 |
| 진행 방식 | 같이 작성 → 하네스 리뷰 → 질문 → 질문이 없으면 다음 단계 |
| 가장 중요한 것 | 페르소나에서 출발한 요구사항 수립 |
| 범위 밖 | 기술 컨벤션, 코드 규칙, 비주얼 디자인 (각 프로젝트 규칙을 따른다) |

---

## 1. 원칙

1. **AI는 자동으로 쓰지 않는다.** 사람이 답한 내용만 문서에 옮긴다.
2. **질문은 입력창으로 작게 한다.** 텍스트가 아니라 선택지 입력창(`AskUserQuestion`)으로 한 번에 1~3개만 묻는다.
3. **단계를 건너뛰지 않는다.** 한 단계의 검토 결과가 0건이어야 다음 단계로 간다.
4. **요구사항은 사람에게서 나온다.** 페르소나의 원하는 것과 행동 패턴에서 출발한다.
5. **기획과 SDD를 섞지 않는다.** 기획은 말로, SDD는 분기 트리로 쓴다.
6. **완성은 셀 수 있어야 한다.** 완성 기준마다 근거 줄이 있어야 완성이다.
7. **판단에는 근거를 단다.** 모델이 "됐다"고 하려면 어느 줄인지 가리켜야 한다.
8. **확정은 사람만 한다.** `상태: 확정`은 사람이 말했을 때만 바꾼다.
9. **한 사실은 한 곳에만 쓴다.** 상태·조건은 표에 한 번 쓰고 트리는 그 이름을 부른다.

---

## 2. 두 문서

| | 기획 | SDD 스펙 |
|---|---|---|
| 읽는 사람 | 비개발자 | 개발자 |
| 파일 | `plan.md` | `sdd.md` |
| 담는 것 | 배경, 페르소나, 요구사항, 완성 기준, 정할 것 | 상태표, 조건표, 진행표, 피쳐·함수 트리 |
| 말투 | 사람이 쓴 것처럼 쉬운 문장 | 조건과 결과가 빠짐없이 드러나는 트리 |
| 작성법 | [기획 작성법](planning-guide.md) | [SDD 스펙 작성법](sdd-guide.md) |
| 순서 | 먼저 | 기획이 확정된 뒤 |

## 3. 전체 흐름

```text
요청 ─▶ 기획 ─────────────────────────────▶ SDD 스펙 ─────────────────────────────────▶ 완료
        배경 → 페르소나 → 요구사항 → 완성 기준 → 확정
                                              상태 → 조건 → 단위 → 트리 → 대조 → 확정
        ▲                                     ▲
        └──── 매 답마다: 옮기기 → check → "추가되어야 완성" → 질문 ────┘
```

- 사람이 새 요구사항을 말하면 기획으로 돌아가 그 요구사항만 추가하고, 진행 중인 단위는 그대로 둔다.
- SDD를 쓰다가 기획과 어긋나는 답이 나오면 SDD에 쓰기 전에 기획을 고칠지 묻는다.
- 기획을 고치면 `상태: 작성중`으로 돌아가고, 다시 확정해야 SDD를 이어 쓴다.

---

## 4. 매 답의 루프

1. 사람이 답한다.
2. AI가 답을 해당 파일의 해당 칸에 옮긴다.
3. AI가 `check`를 돌린다.
4. 걸린 것이 있으면 사람 답이 필요한 것만 질문으로 바꿔 1~3개 묻는다.
5. 형식만 틀린 것(번호 순서, 표 모양)은 묻지 않고 고친 뒤 3으로 돌아간다.
6. 걸린 것이 없으면 하네스가 알려 준 다음 단계를 사람에게 말하고 그 단계 첫 질문을 한다.

보고는 하네스 보고 모양([하네스](harness.md) 4장)을 그대로 보여 주고, 규칙 설명을 되풀이하지 않는다.

## 5. 하네스와 모델의 역할

| 일 | 하네스 | 모델 | 사람 |
|---|---|---|---|
| 문서 내용 정하기 | | | 한다 |
| 질문 만들기 | 걸린 것을 알려 준다 | 사람 말로 바꿔 묻는다 | |
| 답을 문서로 옮기기 | | 한다 | 확인한다 |
| 형식·문장 검사 | 한다 | | |
| 요구사항 대조 | 근거 줄이 실제로 있는지 센다 | 기준마다 근거 줄을 찾는다 | 빠졌다고 나온 것에 답한다 |
| 확정 | 조건이 찼는지 본다 | | 한다 |

## 7. 이전 방식과 다른 점

- v0.9까지는 `spec.json` 하나에서 화면·플로우차트·엣지 케이스를 자동으로 만들었다.
- 자동으로 만든 흐름에는 사람 의도가 빠지고, 기획과 스펙이 섞여 누구에게도 읽기 어려웠다.
- v1.0은 기획과 SDD를 나누고, 흐름은 사람이 분기마다 답해서 만든다.
