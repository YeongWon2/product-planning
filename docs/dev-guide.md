# 개발 스펙 작성법

> 개발 단계다. 확정된 PRD와 기획 상세 스펙에서 질문을 뽑아 개발자를 인터뷰하고, 코드로 알 수 없는 것만 쓴다.
> 시퀀스 다이어그램은 같은 인터뷰 안에서 [다이어그램 작성법](diagram-guide.md)을 따라 `diagram.md`에 쓴다.
> AI는 자동으로 쓰지 않는다. 원문을 인용해 묻고, 개발자가 답한 것만 출처와 함께 옮긴다.

---

## 1. 시작 점검

| 기획 상태 | 하는 일 |
|---|---|
| 기획 폴더가 없다 | 기획 1단계([비즈니스 요구사항](brief-guide.md))부터 시작한다 |
| `brief.md`·`plan.md`·`spec.md` 중 `작성중`이 있다 | 하네스가 알려 주는 멈춘 기획 단계부터 잇는다 |
| 셋 다 `확정`이다 | 아래 단계로 개발 스펙 인터뷰를 시작한다 |

---

## 2. 단계

| 단계 | 질문 재료 (원문을 인용할 곳) | 묻는 것 | 채우는 곳 |
|---|---|---|---|
| 5-1. 결정 | PRD 제약, 범위 밖, 정할 것에서 넘어온 것 | 무엇을 정했고, 왜이며, 무엇을 버렸나 | 결정 기록 |
| 5-2. 아키텍처 | 흐름의 진입 화면, 행동, 외부 결과 | 어떤 구성 요소가 무엇을 책임지고, 무엇에 기대나 | 아키텍처 |
| 5-3. 데이터 | 상태표의 대상·상태, 상태 전이 단계 | 무엇을 저장하고, 깨지면 안 되는 규칙은 무엇인가 | 데이터 모델 |
| 5-4. 계약 | 흐름의 사용자 행동 단계(`사용자가 …`) | 무엇을 보내고, 성공·실패 때 무엇을 받나 | 계약 |
| 5-5. 시퀀스 | 계약과 조건표 갈래 | 누가 누구를 어떤 순서로 부르나 | `diagram.md` |
| 5-6. 오류 | 조건의 실패 갈래, 끊김·중복·동시 수정 | 실패하면 사용자에게 무엇이 보이고 시스템은 무엇을 하나 | 오류·경계 |
| 5-7. 제약 | PRD 목표 지표, 페르소나 행동 패턴 | 속도, 권한, 규모, 보안의 숫자와 조건은 무엇인가 | 비기능 제약 |
| 5-8. 작업 | 요구사항 우선순위 | 먼저 깔아야 할 것과 P1부터의 순서는 무엇인가 | 작업 계획 |
| 5-9. 검증 | 완성 기준 `R1-1` | 무엇을 해 보면 완성인지 확인되나 | 검증 |
| 5-10. 규칙 대조 | 프로젝트의 규칙 파일 (CLAUDE.md, 컨벤션 문서) | 위 결정이 규칙과 어긋나지 않나 | 프로젝트 규칙 대조 |
| 5-11. 확정 | 전체 | 읽고 확정한다 | 상태 `확정` |

한 단계의 검토 결과가 0건이어야 다음으로 간다. 기획의 상태·행동·실패 갈래·완성 기준 하나하나가 질문 재료이며, 대응 항목이 없으면 하네스가 `[안 물어봄]`으로 알린다.

질문 예:

```text
근거  기획 상세 스펙 › F1 › 대안 흐름 › 1a. 수정 권한이 있는가: 아니오
원문  "1a1. 수정 단추가 보이지 않는다"
근거 코드  src/posts/permission.ts:14
질문  권한은 화면과 서버 중 어디서 확인하나요? 서버에서도 막아야 하나요?
```

## 3. 쓰는 것과 쓰지 않는 것

| 쓴다 (코드로 알 수 없다) | 쓰지 않는다 (코드를 보면 안다) |
|---|---|
| 왜 이렇게 정했는지와 버린 대안 | 언어·프레임워크 버전, 폴더 구조 |
| 구성 요소의 책임과 경계, 의존 방향 | 이름 짓기, 코드 스타일, 린트 규칙 |
| 깨지면 안 되는 데이터 규칙 | 이미 있는 테이블의 컬럼 목록 그대로 |
| 성공·실패의 약속과 실패 때 보이는 것 | 라이브러리 사용법 |
| 숫자로 된 제약, 작업 순서, 완성 확인법 | 테스트 도구 설정 |

AI는 코드를 읽어 질문을 구체적으로 만들 수 있지만, 코드에서 읽은 것을 답처럼 쓰지 않는다.
답이 기획과 어긋나면 쓰지 않고 `기획에 돌려보낼 것`에 남긴다.

## 4. 파일 모양

작업 파일과 결과 파일 모두 `dev.md`다. `출처:`는 인용한 원문의 위치이며, 결과물에서는 링크가 된다.

```md
# 게시글 수정 개발 스펙

상태: 작성중

## 결정 기록

### D1 고친 글은 덮어쓰고 이전 글은 남기지 않는다

이유: 고친 기록 보기는 범위 밖이고, 댓글은 글 번호에 붙어 있어 덮어써도 남는다.
버린 대안: 고칠 때마다 새 판을 저장한다 (다음 분기 기록 보기 때 다시 본다).
출처: PRD › 범위 밖 › 고친 기록을 남이 보는 기능은 이번에 하지 않는다.

## 아키텍처

| 번호 | 구성 요소 | 책임 | 하지 않는 것 | 기대는 곳 |
|---|---|---|---|---|
| A1 | 글 화면 | 수정 모달을 열고 닫고 고친 내용을 보낸다 | 권한을 최종 판단하지 않는다 | A2 |
| A2 | 글 서버 | 권한과 상태를 확인하고 글을 바꾼다 | 화면 문구를 정하지 않는다 | A3 |
| A3 | 글 저장소 | 글과 상태를 보관한다 | | |

의존은 A1 → A2 → A3 한 방향이다. 출처: D1

## 데이터 모델

### M1 게시글

| 값 | 뜻 | 규칙 |
|---|---|---|
| 상태 | 상태표의 게시글 상태 | 게시됨, 잠김 중 하나다 |
| 본문 | 글 내용 | 비어 있을 수 없다 |

- 잠김인 글은 본문이 바뀌지 않는다.
- 글을 고쳐도 글 번호는 바뀌지 않는다.

출처: 기획 상세 스펙 › 상태표 › 게시글

## 계약

### C1 글 수정 요청

호출: A1 → A2
입력: 글 번호, 고친 본문
성공: 고친 글
실패: E1
출처: F1 › 기본 흐름 › 3. 사용자가 글을 고치고 저장을 누른다

## 오류·경계

### E1 권한 없음

상황: 남의 글을 고치라는 요청이 왔다.
보이는 것: 저장되지 않았다는 안내가 뜬다.
시스템 처리: 아무것도 바꾸지 않고 거절한다.
출처: F1 › 대안 흐름 › 1a. 수정 권한이 있는가: 아니오

## 비기능 제약

- N1 저장을 누르고 2초 안에 고친 글이 보인다. 출처: P1 행동 패턴 › 글을 올린 직후 휴대폰으로 다시 읽어 본다.

## 작업 계획

### 기반

- [ ] T1 게시글에 상태 값을 둔다. 근거: M1
- 체크포인트: 상태가 저장되고 읽힌다.

### P1 · R1

- [ ] T2 [P] 글 수정 요청을 받는다. 근거: C1, E1
- [ ] T3 [P] 수정 모달을 연다. 근거: F1, FN1
- 체크포인트: V1이 통과한다.

## 검증

- V1 R1-2 · 댓글 2개가 달린 글을 고쳐 저장하면 댓글 2개가 그대로 보인다.

## 프로젝트 규칙 대조

| 규칙 | 원문 | 결과 |
|---|---|---|
| CLAUDE.md:12 | "서버가 권한을 최종 판단한다" | 맞다 (A2, E1) |

## 기획에 돌려보낼 것

## 정할 것
```

`[P]`는 다른 작업과 겹치는 파일이 없어 동시에 해도 되는 작업이다.

`출처:`는 아래 모양 가운데 하나이며, `pp.mjs quotes`가 인용할 수 있는 원문을 모두 내준다.

| 모양 | 예 |
|---|---|
| 번호 (쉼표로 여럿) | `D1`, `BR1, R1-2` |
| 곳 › 원문 | `범위 밖 › …`, `제약 › …`, `왜 지금 › …`, `G1 지표 › …`, `P1 행동 패턴 › …` |
| 표 › 이름 | `상태표 › 게시글`, `조건표 › 수정 권한이 있는가` |
| 흐름 줄 경로 | `F1 › 대안 흐름 › 1a. 수정 권한이 있는가: 아니오` |

앞에 `PRD › `나 `기획 상세 스펙 › `를 붙여도 된다. 원문 끝 마침표는 있어도 없어도 된다.

## 5. 검사 규칙

| 규칙 | 걸리는 경우 |
|---|---|
| 출처 없음 | `D` `M` `C` `E` `N` 항목에 `출처:`가 없다 |
| 출처 낡음 | `출처:`의 원문이 지금 기획 문서에 그대로 없다 |
| 안 물어봄 | PRD 제약(5-1), 상태표 대상(5-3), 흐름 행동(5-4, 그 줄이나 그 위 흐름·갈림 인용), 조건(5-6), 요구사항(5-8)을 인용한 항목이 없다 |
| 없는 구성 요소 | 계약의 `호출:`이나 의존에 아키텍처 표에 없는 `A`가 나온다 |
| 거꾸로 의존 | 계약의 `호출: A1 → A2`인데 A1의 `기대는 곳`에 A2가 없다 |
| 이름 없는 실패 | 계약의 `실패:`가 가리키는 `E`가 없다 |
| 근거 없는 작업 | `T`에 `근거:`가 없거나 없는 번호를 가리킨다 |
| 검증 없는 기준 | 제외되지 않은 완성 기준에 `V`가 없다 |
| 그림 없는 계약 | 어느 시퀀스에도 나오지 않는 `C`가 있다 |
| 남은 것 | `기획에 돌려보낼 것`이나 `정할 것`이 남았다 |
