# 기획 상세 스펙 작성법

> 기획 4단계다. PRD가 확정된 뒤, 요구사항을 진입부터 결과까지 조건·상태 분기 트리로 펼친다.
> 기획자와 개발자가 같이 읽으며, 개발 스펙([작성법](dev-guide.md))의 질문 재료가 된다.
> AI는 자동으로 쓰지 않는다. 단계를 이끌고 빠진 분기를 원문 인용으로 질문하며, 사람이 답한 내용만 옮긴다.

---

## 1. 단계

| 단계 | 사람이 하는 일 | AI가 하는 일 | 끝나는 조건 |
|---|---|---|---|
| 4-1. 상태 수립 | 대상마다 가질 수 있는 상태와 뜻을 답한다 | 요구사항을 인용해 "게시글은 어떤 상태를 거치나요?"처럼 묻는다 | 상태표가 비지 않았다 |
| 4-2. 조건 수립 | 흐름을 가르는 조건과 갈래를 답한다 | 권한·입력·수정 여부·외부 결과처럼 갈래가 생길 곳을 묻는다 | 조건표가 비지 않았다 |
| 4-3. 단위 나누기 | 피쳐와 함수 목록, 쓸 순서를 정한다 | 요구사항을 피쳐로 묶고 반복될 흐름을 함수 후보로 묻는다 | 모든 요구사항이 어느 피쳐에 들어갔다 |
| 4-4. 단위별 트리 | 단위 하나씩 분기와 결과를 답한다 | 재료표와 완성 기준을 인용해 다음 분기를 묻는다 | 그 단위의 형식 검사가 0건이다 |
| 4-5. 요구사항 대조 | 빠졌다고 나온 것에 답한다 | 완성 기준마다 근거 줄을 찾아 대조표를 쓴다 | 모든 완성 기준이 근거 줄과 이어졌다 |
| 4-6. 확정 | 전체를 읽고 확정한다 | 남은 검토 결과가 없는지 확인한다 | 상태를 `확정`으로 바꾼다 |

재료(상태·조건)를 먼저 세우고, 트리는 단위 하나씩 쓴다.
트리를 쓰다가 표에 없는 상태나 조건이 나오면 트리에 바로 쓰지 않고 표부터 고친다.
확정되면 "개발 스펙으로 넘어갈까요?"를 묻는다. 기술 컨벤션과 코드 규칙은 이 문서의 범위가 아니다.

질문 예:

```text
근거  기획 PRD › R1-2
원문  "고친 뒤에도 댓글이 그대로 남는다"
질문  저장을 누른 뒤 화면에는 무엇이 보이나요? 댓글은 어디에 보이나요?
```

## 2. 판단 근거

| 정할 것 | 결정 | 이유 |
|---|---|---|
| 원본 형식 | md 중첩 목록 | 상자 선(`├─`) 트리는 한 줄만 고쳐도 선을 다시 맞춰야 한다 |
| 재료를 먼저 세우는 이유 | 상태·조건 표를 트리보다 먼저 쓴다 | 표가 있어야 빠진 상태와 갈래를 셀 수 있다 |
| 트리 하나의 범위 | 피쳐 하나 또는 함수 하나 | 사람이 한 번에 답할 수 있는 크기로 자른다 |
| 깊이 | 분기(`?` `◆`) 중첩 3단계까지 | 더 깊으면 눈으로 가지를 따라가지 못하므로 함수로 잘라낸다 |
| 반복되는 흐름 | 함수로 한 번만 쓰고 호출한다 | 복사하면 한쪽만 고쳐지는 일이 생긴다 |
| 번호 | 피쳐 `F1`, 함수 `FN1` | 개발 스펙과 다이어그램이 트리를 번호로 부르고 링크한다 |

## 3. 줄 표기

한 줄에 한 문장만 쓰고, 줄 맨 앞 표시로 종류를 구분한다.

| 표시 | 종류 | 쓰는 법 | 예 |
|---|---|---|---|
| `## F숫자 · 이름 · R번호` | 피쳐 트리 | 진입부터 시작하며 요구사항 번호를 쉼표로 잇는다 | `## F1 · 게시글 수정 · R1` |
| `## FN숫자 · 이름` | 함수 트리 | 여러 곳에서 부르는 흐름이다 | `## FN1 · 수정 중 닫기` |
| `?` | 조건 분기 | 조건표의 조건을 그대로 쓴다 | `? 수정 권한이 있는가` |
| `◆ 대상 상태` | 상태 분기 | 상태표의 그 대상 상태를 모두 갈래로 둔다 | `◆ 게시글 상태` |
| `**갈래**` | 갈래 | 분기 바로 아래 줄이다 | `**아니오**` |
| `[단추] 누름` | 사용자 행동 | 누르거나 하는 동작이다 | `[수정] 누름` |
| `→` | 결과 | 화면에 보이는 변화다 | `→ 수정 모달이 열린다` |
| `⇒ 앞 → 뒤` | 상태 전이 | 데이터 상태가 바뀐다 | `⇒ 게시됨 → 검토중` |
| `↪ FN숫자 이름` | 함수 호출 | 함수 트리로 넘긴다 | `↪ FN1 수정 중 닫기` |

줄 경로는 `F1 › ? 수정 권한이 있는가 › **예** › …`처럼 쓰며, 개발 스펙의 `출처:`가 이 경로를 부른다.

## 4. 파일 모양

작업 파일과 결과 파일 모두 `spec.md`다. 결과물에서는 상태 줄과 진행표가 빠지고 번호가 링크가 된다.

```md
# 게시글 수정 기획 상세 스펙

상태: 작성중

## 상태표

| 대상 | 상태 | 뜻 |
|---|---|---|
| 게시글 | 게시됨 | 모두에게 보이는 글이다 |
| 게시글 | 잠김 | 신고가 쌓여 관리자가 막은 글이다 |

## 조건표

| 조건 | 갈래 | 정해지는 곳 |
|---|---|---|
| 수정 권한이 있는가 | 예, 아니오 | 글쓴이 본인이면 예다 |
| 고친 내용이 있는가 | 예, 아니오 | 모달을 연 뒤 한 글자라도 바뀌면 예다 |

## 진행표

| 단위 | 이름 | 요구사항 | 진행 |
|---|---|---|---|
| F1 | 게시글 수정 | R1 | 작성중 |
| FN1 | 수정 중 닫기 | R1 | 완료 |

## F1 · 게시글 수정 · R1

- [게시글 상세] 진입
- ? 수정 권한이 있는가
  - **아니오**
    - → [수정] 단추가 보이지 않는다
  - **예**
    - ◆ 게시글 상태
      - **게시됨**
        - [수정] 누름 → 수정 모달이 열린다
        - [저장] 누름 → 고친 글이 보이고 댓글은 그대로 남는다
        - ↪ FN1 수정 중 닫기
      - **잠김**
        - → [수정] 단추가 비활성이다

## FN1 · 수정 중 닫기

- [닫기] 누름
  - ? 고친 내용이 있는가
    - **아니오**
      - → 모달이 바로 닫힌다
    - **예**
      - → "저장하지 않고 닫을까요?" 확인창이 뜬다
      - [닫기] 누름 → 모달이 닫히고 고친 내용은 버려진다
      - [취소] 누름 → 모달이 그대로 남는다
```

진행표의 진행은 `대기`, `작성중`, `완료` 중 하나이며, 중간에 멈춰도 여기서 이어서 쓴다.

## 5. 형식 검사 규칙

| 규칙 | 걸리는 경우 |
|---|---|
| 끝 없는 가지 | 형제 가운데 마지막 줄이 자식도 없고 `→` `⇒` `↪`도 없다 |
| 빠진 갈래 | `?` 아래에 조건표의 갈래가 다 나오지 않았다 |
| 빠진 상태 | `◆` 아래에 상태표의 그 대상 상태가 다 나오지 않았다 |
| 없는 재료 | 표에 없는 조건·대상·상태를 트리에서 썼다 |
| 너무 깊은 트리 | 분기 중첩이 3단계를 넘는다 |
| 없는 함수 | `↪`가 가리키는 `FN` 트리가 없다 |
| 안 쓰인 재료 | 어느 트리에도 나오지 않은 상태나 조건이 있다 |
| 피쳐 없는 요구사항 | PRD의 요구사항이 어느 피쳐에도 없다 |
| 진행표 불일치 | 진행표와 트리 제목이 서로 맞지 않는다 |
| 한 줄 두 문장 | 한 줄에 문장이 둘 이상이다 |

## 6. 요구사항 대조

형식 검사만으로는 요구사항대로 됐는지 알 수 없으므로, 모델이 완성 기준마다 근거 줄을 찾아 `trace.json`에 적는다.

- 하네스의 `sheet` 명령이 완성 기준 목록과 트리의 모든 줄 경로를 내준다.
- 모델은 기준마다 `met`(근거 줄이 있다) 또는 `missing`(빠졌다)을 적는다.
- `met`이면 근거 줄 경로를 하나 이상 적어야 한다.
- `missing`이면 무엇이 추가돼야 완성인지 한 문장으로 적고, 트리에는 직접 쓰지 않는다.
- 기준 문장이나 근거 줄이 바뀌면 하네스가 그 판단을 낡은 것으로 보고 다시 판단하게 한다.
- 대조 파일의 모양은 [하네스](harness.md) 3장을 따른다.
