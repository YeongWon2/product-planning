# 기획 상세 스펙 작성법

> 기획 4단계다. PRD가 확정된 뒤, 요구사항을 유스케이스 명세 틀(기본 흐름 · 대안 흐름 · 예외 흐름)로 펼친다.
> 비개발자가 화면 흐름을 글로 적은 문서라 기호와 그림 없이 번호와 낱말만 쓴다. 그림은 개발 스펙의 [시퀀스 다이어그램](diagram-guide.md)이 맡는다.
> 기획자와 개발자가 같이 읽으며, 개발 스펙([작성법](dev-guide.md))의 질문 재료가 된다.
> AI는 자동으로 쓰지 않는다. 단계를 이끌고 빠진 분기를 원문 인용으로 질문하며, 사람이 답한 내용만 옮긴다.

---

## 1. 단계

| 단계 | 사람이 하는 일 | AI가 하는 일 | 끝나는 조건 |
|---|---|---|---|
| 4-1. 상태 수립 | 대상마다 가질 수 있는 상태와 뜻을 답한다 | 요구사항을 인용해 "게시글은 어떤 상태를 거치나요?"처럼 묻는다 | 상태표가 비지 않았다 |
| 4-2. 조건 수립 | 흐름을 가르는 조건과 갈래를 답한다 | 권한·입력·수정 여부·외부 결과처럼 갈래가 생길 곳을 묻는다 | 조건표가 비지 않았다 |
| 4-3. 단위 나누기 | 피쳐와 함수 목록, 쓸 순서를 정한다 | 요구사항을 피쳐로 묶고 반복될 흐름을 함수 후보로 묻는다 | 모든 요구사항이 어느 피쳐에 들어갔다 |
| 4-4. 단위별 흐름 | 기본 흐름, 갈래마다 대안 흐름, 실패할 때 예외 흐름을 답한다 | 단계마다 "여기서 다르게 되는 경우는?", "실패하면?"을 묻는다 | 그 단위의 형식 검사가 0건이다 |
| 4-5. 요구사항 대조 | 빠졌다고 나온 것에 답한다 | 완성 기준마다 근거 줄을 찾아 대조표를 쓴다 | 모든 완성 기준이 근거 줄과 이어졌다 |
| 4-6. 확정 | 전체를 읽고 확정한다 | 남은 검토 결과가 없는지 확인한다 | 상태를 `확정`으로 바꾼다 |

재료(상태·조건)를 먼저 세우고, 흐름은 단위 하나씩 쓴다.
흐름을 쓰다가 표에 없는 상태나 조건이 나오면 흐름에 바로 쓰지 않고 표부터 고친다.
확정되면 "개발 스펙으로 넘어갈까요?"를 묻는다. 기술 컨벤션과 코드 규칙은 이 문서의 범위가 아니다.

질문 예:

```text
근거  기획 PRD › R1-2
원문  "고친 뒤에도 댓글이 그대로 남는다"
질문  저장을 누른 뒤 화면에는 무엇이 보이나요? 저장이 실패하면 어떻게 되나요?
```

## 2. 판단 근거

| 정할 것 | 결정 | 이유 |
|---|---|---|
| 틀 | 유스케이스 명세의 기본 흐름 · 대안 흐름 · 예외 흐름 | Cockburn과 RUP 유스케이스 명세가 쓰는 틀이라 기획자와 개발자가 같은 말로 읽는다 |
| 표기 | 번호와 낱말만 쓴다 | 메모장, 메신저, 인쇄 어디서 읽어도 흐름이 보여야 한다. 그림은 시퀀스 다이어그램이 맡는다 |
| 갈림 번호 | 갈라진 단계 번호 뒤에 a, b를 붙인다 (`3a`, 처리 단계 `3a1`) | 어느 단계에서 갈라졌는지 번호만 보고 안다 |
| 갈림의 끝 | "N으로 돌아간다", "끝난다", "FN번호 이름을 따른다" 중 하나 | 갈라진 뒤 어디로 가는지 빠짐없이 닫힌다 |
| 대안과 예외 | 대안은 조건표·상태표의 갈래, 예외는 실패와 끊김이다 | 예외는 개발 스펙의 오류(`E`) 질문 재료가 된다 |
| 재료를 먼저 세우는 이유 | 상태·조건 표를 흐름보다 먼저 쓴다 | 표가 있어야 빠진 갈래를 셀 수 있다 |
| 깊이 | 갈림 안의 갈림은 3단계까지 | 더 깊으면 눈으로 따라가지 못하므로 함수로 잘라낸다 |
| 반복되는 흐름 | 함수로 한 번만 쓰고 부른다 | 복사하면 한쪽만 고쳐지는 일이 생긴다 |
| 번호 | 피쳐 `F1`, 함수 `FN1` | 개발 스펙과 다이어그램이 흐름을 번호로 부르고 링크한다 |

## 3. 줄 표기

한 줄에 한 문장만 쓴다. 단계는 `- 번호. 문장` 목록으로 쓰고, 갈림의 처리 단계는 한 칸 들여 쓴다.

| 줄 | 종류 | 쓰는 법 | 예 |
|---|---|---|---|
| `## F숫자 · 이름 · R번호` | 피쳐 | 요구사항 번호를 쉼표로 잇는다 | `## F1 · 게시글 수정 · R1` |
| `## FN숫자 · 이름` | 함수 | 여러 곳에서 부르는 흐름이다 | `## FN1 · 수정 중 닫기` |
| `시작:` | 시작 | 사용자가 어디서 시작하는지 쓴다 (피쳐는 꼭 쓴다) | `시작: 사용자가 게시글 상세 화면을 연다` |
| `전제:` | 기본 흐름의 갈래 | 기본 흐름이 따르는 조건·상태를 `조건: 갈래`로 쓴다 | `전제: 수정 권한이 있는가: 예` |
| `### 기본 흐름` | 기본 흐름 | 모든 일이 잘될 때의 단계를 1, 2, 3으로 쓴다 | `- 1. 사용자가 수정을 누른다` |
| `### 대안 흐름` | 대안 흐름 | 다른 갈래나 사용자의 다른 선택이다 | `- 1a. 수정 권한이 있는가: 아니오` |
| `### 예외 흐름` | 예외 흐름 | 실패하거나 끊겼을 때다. 없으면 `- 없음: 이유` | `- 3b. 저장이 실패한다` |
| `사용자가 …` | 사용자 행동 | 사용자가 하는 동작이다 | `3. 사용자가 저장을 누른다` |
| 그 밖의 단계 | 화면 결과 | 화면에 보이는 변화다 | `2. 수정 모달이 열린다` |
| `…에서 …로 바뀐다` | 상태 전이 | 상태표의 두 상태를 쓴다 | `게시글이 게시됨에서 검토중으로 바뀐다` |
| `N으로 돌아간다` · `끝난다` | 갈림의 끝 | 갈림의 마지막 단계다 | `3b2. 2로 돌아간다` |
| `FN숫자 이름을 따른다` | 함수 호출 | 함수 흐름으로 넘긴다 | `3a1. FN1 수정 중 닫기를 따른다` |

갈림 머리에 `조건: 갈래` 또는 `대상 상태: 상태`를 쓰면 표의 말이어야 한다. 사용자 선택이나 실패처럼 표에 없는 갈림은 쌍점 없이 쓴다.
줄 경로는 `F1 › 대안 흐름 › 1a. 수정 권한이 있는가: 아니오 › 1a1. 수정 단추가 보이지 않는다`처럼 쓰며, 개발 스펙의 `출처:`가 이 경로를 부른다.

## 4. 파일 모양

작업 파일과 결과 파일 모두 `spec.md`다. 결과물에서는 상태 줄과 진행표가 빠지고 번호가 링크가 된다.

```md
# 게시글 수정 기획 상세 스펙

상태: 작성중

## 상태표

| 대상 | 상태 | 뜻 |
|---|---|---|
| 게시글 | 게시됨 | 모두에게 보이는 글이다 |
| 게시글 | 잠김 | 신고가 쌓여 관리자가 막은 글이다 |

## 조건표

| 조건 | 갈래 | 정해지는 곳 |
|---|---|---|
| 수정 권한이 있는가 | 예, 아니오 | 글쓴이 본인이면 예다 |

## 진행표

| 단위 | 이름 | 요구사항 | 진행 |
|---|---|---|---|
| F1 | 게시글 수정 | R1 | 작성중 |

## F1 · 게시글 수정 · R1

시작: 사용자가 게시글 상세 화면을 연다
전제: 수정 권한이 있는가: 예
전제: 게시글 상태: 게시됨

### 기본 흐름

- 1. 사용자가 수정을 누른다
- 2. 수정 모달이 열린다
- 3. 사용자가 글을 고치고 저장을 누른다
- 4. 고친 글이 보이고 댓글은 그대로 남는다

### 대안 흐름

- 1a. 수정 권한이 있는가: 아니오
  - 1a1. 수정 단추가 보이지 않는다
  - 1a2. 끝난다
- 1b. 게시글 상태: 잠김
  - 1b1. 수정 단추가 비활성이다
  - 1b2. 끝난다

### 예외 흐름

- 3b. 저장이 실패한다
  - 3b1. 저장되지 않았다는 안내가 뜬다
  - 3b2. 2로 돌아간다
```

진행표의 진행은 `대기`, `작성중`, `완료` 중 하나이며, 중간에 멈춰도 여기서 이어서 쓴다.
함수 줄의 요구사항 칸은 비워도 된다. 결과물을 다시 읽어 오면 진행표는 흐름에서 새로 만든다.

## 5. 형식 검사 규칙

| 규칙 | 걸리는 경우 |
|---|---|
| 기호 | 화살표, 굵게, 이모지 같은 기호를 썼다 |
| 시작 없음 · 빈 흐름 | 피쳐에 `시작:`이 없거나 기본 흐름 단계가 없다 |
| 예외 흐름 없음 | 피쳐에 예외 흐름도 `없음: 이유`도 없다 |
| 번호 순서 · 번호 없는 줄 | 기본 흐름이 1부터 차례가 아니거나, 처리 단계가 갈림 번호로 시작하지 않거나, 번호가 없다 |
| 없는 단계 | 갈림이 나온 단계나 돌아가는 단계가 없다 |
| 끝 없는 흐름 | 갈림의 마지막 단계가 돌아간다·끝난다·따른다가 아니다 |
| 빠진 갈래 · 빠진 상태 | 쓰인 조건·상태의 갈래가 전제와 대안 흐름에 다 나오지 않았다 |
| 없는 재료 | 표에 없는 조건·대상·상태를 썼다 |
| 너무 깊은 흐름 | 갈림 안의 갈림이 3단계를 넘는다 |
| 없는 함수 · 안 쓰인 함수 | 부르는 `FN`이 없거나, 아무도 부르지 않는 `FN`이 있다 |
| 안 쓰인 재료 | 어느 흐름에도 나오지 않은 상태나 조건이 있다 |
| 피쳐 없는 요구사항 | PRD의 요구사항이 어느 피쳐에도 없다 |
| 진행표 불일치 | 진행표와 흐름 제목이 서로 맞지 않는다 |
| 한 줄 두 문장 | 한 줄에 문장이 둘 이상이다 |

## 6. 요구사항 대조

형식 검사만으로는 요구사항대로 됐는지 알 수 없으므로, 모델이 완성 기준마다 근거 줄을 찾아 `trace.json`에 적는다.

- 하네스의 `sheet` 명령이 완성 기준 목록과 흐름의 모든 줄 경로를 내준다.
- 모델은 기준마다 `met`(근거 줄이 있다) 또는 `missing`(빠졌다)을 적는다.
- `met`이면 근거 줄 경로를 하나 이상 적어야 한다.
- `missing`이면 무엇이 추가돼야 완성인지 한 문장으로 적고, 흐름에는 직접 쓰지 않는다.
- 기준 문장이나 근거 줄이 바뀌면 하네스가 그 판단을 낡은 것으로 보고 다시 판단하게 한다.
- 대조 파일의 모양은 [하네스](harness.md) 3장을 따른다.
