# 개발 스펙 같이 쓰기

폴더: $ARGUMENTS

폴더가 이름만이면 대상 프로젝트의 `.product-planning/{이름}/`으로 읽는다. 비어 있으면 그 아래 폴더 목록과, 대상 프로젝트 `docs/product/` 아래 기능 목록을 입력창 선택지로 보여 주고 고르게 한다.

- 설계: 이 스킬 폴더 기준 `../../docs/design.md` — 시작할 때 한 번 읽는다
- 작성법: `../../docs/dev-guide.md`, `../../docs/diagram-guide.md` — 시작할 때 읽는다
- 하네스: `node <플러그인 루트>/scripts/pp.mjs` (플러그인 루트 = 이 스킬 폴더의 두 단계 위), 명령과 보고 모양은 `../../docs/harness.md`

## 1. 지켜야 할 것

- 개발 스펙은 개발자가 정한다. AI는 기획 원문을 인용해 묻고, 답한 것만 출처와 함께 옮긴다.
- 코드로 알 수 있는 것(언어 버전, 폴더 구조, 이름 짓기, 코드 스타일)은 쓰지 않는다 (dev-guide 3장).
- AI는 코드를 읽어 질문을 구체적으로 만들 수 있다. 질문에 `근거 코드  경로:줄`을 붙이되, 코드에서 읽은 것을 답처럼 쓰지 않는다.
- 답이 기획과 어긋나면 개발 스펙에 쓰지 않고 `## 기획에 돌려보낼 것`에 남긴 뒤, 기획을 고칠지 입력창으로 묻는다. 고치면 `/yw-plan`의 절차로 그 문서를 작성중으로 돌려 고치고 다시 확정받는다.
- 다이어그램은 자동으로 그리지 않는다. 개발자가 답한 순서만 옮긴다.
- `상태: 확정`은 개발자가 확정한다고 말했을 때만 바꾼다. 작업 파일은 작업 폴더에만 둔다.

## 2. 시작

1. 작업 폴더가 없고 프로젝트에 `docs/product/{기능}/`가 있으면 `pp.mjs import <프로젝트> <폴더>`로 읽어 온다.
2. 둘 다 없으면 기획부터 해야 한다고 알리고 `/yw-plan <기능>`의 절차로 1단계부터 시작한다.
3. `pp.mjs check <폴더>`를 돌린다.
   - 단계가 `기획 › …`이면 그 기획 단계가 남았다고 알리고 `/yw-plan`의 절차로 그 단계부터 잇는다.
   - 단계가 `기획 완료`이면 `pp.mjs init <폴더>`로 `dev.md`·`diagram.md` 틀을 만든다.
4. `pp.mjs quotes <폴더>`로 인용할 수 있는 원문 목록을 받아 둔다. 기획 문서가 바뀌면 다시 받는다.
5. 지금 단계의 첫 질문을 한다.

## 3. 매 답의 루프

1. 개발자가 답한다.
2. 답을 `dev.md` 또는 `diagram.md`의 해당 칸에 옮기고, 질문에 인용한 원문을 `출처:`에 그대로 쓴다.
3. `pp.mjs check <폴더>`를 돌린다.
4. 보고의 "추가되어야 완성" 가운데 사람 답이 필요한 것을 원문 인용 질문 1~3개로 바꿔 `AskUserQuestion`으로 묻는다.
5. 표 모양, 번호, 들여쓰기처럼 형식만 틀린 것은 묻지 않고 고친 뒤 3으로 돌아간다.
6. 걸린 것이 없어 단계가 바뀌면 한 줄로 알리고 그 단계 첫 질문을 한다.

`안 물어봄`이 나오면 그 기획 줄이 질문 재료다. 그 줄을 인용해 묻는다. `출처 낡음`이 나오면 quotes를 다시 받아 원문이 어떻게 바뀌었는지 보여 주고, 답이 그대로인지 묻는다.

## 4. 질문 모양

```text
header: C1 권한
question: |
  근거  기획 상세 스펙 › F1 › 대안 흐름 › 1a. 수정 권한이 있는가: 아니오
  원문  "1a1. 수정 단추가 보이지 않는다"
  근거 코드  src/posts/permission.ts:14
  권한은 화면과 서버 중 어디서 확인하나요? 서버에서도 막아야 하나요?
options:
  - 서버가 최종 판단, 화면은 숨기기만 (추천) — CLAUDE.md:12 규칙과 같아서
  - 화면에서만 막는다
```

- 원문은 quotes 목록의 `quote`를 한 글자도 바꾸지 않고 쓴다.
- 한 번에 질문 1~3개, 선택지 2~4개. 추천은 첫 선택지에 `(추천)`과 이유 한 줄.
- 답 후보는 기획 문서, 코드에서 읽은 사실, 프로젝트 규칙에서만 만든다.
- 시퀀스를 물을 때는 선택지마다 `preview`에 그 답을 고르면 그림이 어떻게 되는지 Mermaid 조각을 넣는다.

## 5. 단계마다 묻는 법

| 단계 | 인용할 원문 | 묻는 것 |
|---|---|---|
| 5-1 결정 | PRD 제약, 범위 밖 | 무엇을 정했고, 왜이며, 무엇을 버렸나 |
| 5-2 아키텍처 | 흐름 진입·행동 | 어떤 구성 요소가 무엇을 책임지고, 무엇에 기대나 |
| 5-3 데이터 | 상태표 대상 | 무엇을 저장하고, 깨지면 안 되는 규칙은 무엇인가 |
| 5-4 계약 | 흐름 사용자 행동 | 무엇을 보내고 성공·실패 때 무엇을 받나 |
| 5-5 시퀀스 | 계약, 조건표 갈래 | 누가 누구를 어떤 순서로 부르나, 갈래마다 무엇이 오가나 |
| 5-6 오류 | 조건의 실패 갈래 | 실패하면 무엇이 보이고 시스템은 무엇을 하나 |
| 5-7 제약 | PRD 지표, 페르소나 행동 패턴 | 속도·권한·규모·보안의 숫자와 조건 |
| 5-8 작업 | 요구사항 우선순위 | 먼저 깔 것, P1부터의 순서, 동시에 해도 되는 것 |
| 5-9 검증 | 완성 기준 | 무엇을 해 보면 완성인지 확인되나 |
| 5-10 규칙 대조 | 프로젝트 규칙 파일 | 위 결정이 규칙과 어긋나지 않나 |

- 5-10은 AI가 프로젝트의 CLAUDE.md, 컨벤션 문서를 읽고 대조할 줄을 뽑아 개발자에게 확인받는다. 규칙 파일이 없으면 "규칙 파일 없음" 한 줄을 확인받아 쓴다.
- 시퀀스의 참여자는 아키텍처 표의 번호와 이름, 갈래는 조건표 그대로 쓴다 (diagram-guide 3장).

## 6. 끝

- 보고 단계가 `완료`이고 종료 코드가 0이면 네 문서가 끝난 것이다. 결정·계약·작업·시퀀스 수를 한 줄로 알린다.
- 대상 프로젝트 폴더를 입력창으로 확인한다. 기본은 지금 대화를 연 프로젝트다.
- `pp.mjs export <폴더>`로 `docs/product/{기능}/`에 네 문서를 쓰고 작업 폴더를 지운다. 파일이 이미 있으면 덮어쓸지 먼저 묻고 `--force`를 붙인다.
- 네 결과물 경로를 알린다.
