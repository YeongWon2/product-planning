# 기획서 파이프라인

요청: $ARGUMENTS

요청이 비어 있으면 "무엇을 기획할까요? 누가 무엇을 하는지 한 줄로 알려 주세요."라고만 묻고 기다린다.

이 스킬은 기획을 **요소와 관계로 이루어진 모델**(`spec.json`)로 만들고, 규칙으로 검사해, 같은 모양의 HTML로 빌드한다. 사람이 고치는 파일은 `spec.json` 하나뿐이다.

- 형식 계약: 이 스킬 폴더 기준 `../../docs/산출물-명세.md` — `spec.json`을 쓰기 전에 2장을 읽는다
- 설계 배경: `../../docs/설계서.md` — 단계(4장), 흐름 규칙(4.1절), 검토 기준(5장)이 필요할 때만 읽는다
- 명령: `node <플러그인 루트>/scripts/spec.mjs check|build <spec.json>` (플러그인 루트 = 이 스킬 폴더의 두 단계 위)

## 1. 요청한 것만 다룬다

- 요구사항은 요청 문장과 사용자가 답한 것에서만 만든다. 요청에 없는 기능·화면·알림을 제안해 넣지 않는다.
- 검사가 요구하는 칸(다른 사용자 유형의 동작 가능표, 상태 전이, 실패 처리 등)은 요청 범위 안의 빈칸이므로 채운다. 새 기능이 아니다.
- 요청 밖으로 보이지만 떠오른 것은 넣지 않고, 필요하면 `summary.outOfScope`(이번에 하지 않는 것)에 한 줄로만 적는다.
- `request-scope` 경고(어느 시나리오에서도 쓰이지 않는 동작, 동작이 없는 개체)는 요청 밖이라는 신호다. 빼거나, 요청에 필요하면 시나리오에 넣는다.

## 2. 입구 고르기

| 사용자가 가진 것 | 입구 | 시작점 |
|---|---|---|
| 요청 문장만 | 새로 만들기 | 단계 1 정의부터 빈 곳만 묻는다 |
| 요청에 기획 문서·디자인 메모·티켓 같은 자료가 함께 있음 | 보완하기 | 자료를 읽고 사실을 요소로 옮긴 뒤 빈 곳만 묻는다 |
| 이미 있는 `spec.json` + 바꿀 내용 | 변경하기 | 바꿀 요소와 영향받는 요소만 다룬다 |

`spec.json` 위치를 사용자가 정하지 않았으면 `specs/{기능 이름}/spec.json`에 만들고 경로만 알린다.

## 3. 채우는 순서

설계서 4장 단계를 따른다. 앞 단계가 비면 다음 단계로 넘어가지 않는다.

1. **정의**: 해결할 문제와 그 근거, 누구를 위한 것인지, 목표 지표, 이번에 하지 않는 것
2. **시나리오**: 요구사항 한 줄씩 ("누가 무엇을 한다"), 요구사항마다 단계 (누가, 어느 앱에서, 어떤 동작)
3. **모델링**: 개체와 상태·전이, 동작 (종류 `list`·`view`·`create`·`update`·`delete`·`other`, 입력 항목과 검증 규칙, 되돌릴 수 있는지, 다른 앱 영향), 동작 가능표의 칸
   - 기한 도래·기간 종료처럼 사람이 아니라 규칙으로 일어나는 상태 변화는 `automatic: true`인 사용자 유형(예: 시스템)의 단계로 적는다. 그 단계는 결과가 보이는 상세·목록 화면에 연결된다 (F12)

아래는 도구가 파생하므로 `spec.json`에 적지 않는다.

- 화면, 화면 이동, 모달·확인 창 — 흐름 규칙 F1~F12가 만든다. 판단을 바꾸려면 `flowOverrides`와 `decisions`에 적는다
- 플로우차트(판단 분기) — 동작 가능표·입력 규칙·확인 창·실패 안내에서 나온다 (FC1~FC4)
- 완료 조건 초안 — 동작 가능표와 상태 전이에서 나온다. 사람이 확정한 것만 `acceptance`에 적는다
- 동작 가능표 빈칸에서 나오는 질문

## 4. 사실을 지어내지 않는다

- 모든 사실에는 `source`를 단다. 사용자가 말했거나 문서에서 읽은 것은 `doc`·`data` 등과 위치(`ref`), 근거가 없으면 `{ "kind": "assumption" }`.
- 출처 위치(`ref`)는 기호 없이 '문서 이름 · 번호 제목'으로 적는다. 예: `코치 PRD · 5.1.2 팀 목표 기간 수정`. 여러 곳이면 쉼표로 잇는다. 기획서 안의 글(결정·질문·안내 문구 등)과 사용자에게 하는 말에도 `§` 같은 기호를 쓰지 않는다 (`plain-text` 경고).
- 모르는 것은 채우지 않고 사용자에게 묻는다. 답을 기다리는 동안은 `questions`에 담당자(`owner`)와 착수를 막는지(`blocking`)를 함께 적는다.
- 동작 가능표 칸을 추측으로 채우지 않는다.
- 보완하기에서 두 자료가 서로 다르게 말하면 한쪽을 고르지 않고 충돌로 묻는다.

## 5. 100%까지 반복한다

완료 기준은 `check` 결과가 **착수 가능**이고 **검사 통과율 100%**(경고 0건 포함)인 것이다.

1. `check`를 돌린다. 종료 코드 0 = 착수 가능, 1 = 착수 불가, 2·3 = 입력·경로 오류.
2. 사람 답이 필요 없는 이슈(형식, 참조, 파생 규칙 위반)는 묻지 않고 고친다.
3. 사람 답이 필요한 것은 질문으로 바꿔 한 번에 1~3개만 묻는다. 답을 받으면 `spec.json`에 반영하고 1로 돌아간다.
4. 멈추는 경우는 둘뿐이다: 100%가 됐다 / 한 바퀴를 돌았는데 통과 수가 늘지 않았다(막힌 이슈와 이유를 보고한다).

질문은 짧게 쓴다. 선택지가 있으면 2~3개를 주고, 추천이 있으면 첫 번째에 이유 한 줄과 함께 둔다.

```
[빈칸] '담당자'가 '완료' 상태의 '항목'을 고칠 수 있나요?
1. 불가 (추천: 완료 뒤 기록이 바뀌지 않게)
2. 허용
```

## 6. 빌드와 보고

- 100%가 되면 `build <spec.json> --open`으로 `out/{폴더 이름}.html`과 `out/report.json`을 만들고, 만든 HTML을 기본 브라우저 창으로 열어 사용자가 바로 확인하게 한다. 창을 열지 못했다는 안내가 나오면 파일 경로를 알려 준다.
- 보고는 다섯 줄 안에서 끝낸다: 파일 경로, 통과율, 요구사항·시나리오·화면 수, 가정으로 남은 사실 수, (있으면) 이번에 하지 않는 것으로 적은 것.
- 진행 중에는 매 바퀴 `검사 N개 중 M개 통과 (X%)` 한 줄과 질문만 보여 준다. 규칙 설명이나 이미 한 일을 되풀이하지 않는다.
- 디자인 도구·문서 도구·이슈 트래커로 옮기는 것은 사용자가 대상을 정하고 확인한 뒤에만 한다. 옮길 내용은 HTML 안의 `<script type="application/json" id="spec-model">` 모델 데이터에서 읽는다 (설계서 9장).
